# Test Priority — E2E Attendance: ESS submits, Admin/Supervisor actions

> Input: `docs/test-strategy_E2E Attendance. ESS submit timesheet and admin or supervisor do the actions.md` (E2E-layer scenarios only).
> Generated by `/define-priority`. Consumed by `/generate-tests`.

Only **E2E** scenarios are prioritized (API/Component/Unit excluded per the skill). Priority reflects
business impact, failure risk, and user reach for the cross-role timesheet approval lifecycle.

---

## P0 — Release-blocking (core flow, security, data integrity, no workaround)

| ID | Scenario | Rationale |
|---|---|---|
| TC-001 | ESS submits → Admin approves (golden path) | The entire feature in one journey; if this breaks, the lifecycle is non-functional. Data integrity (approval gates report hours). No workaround. |
| TC-002 | ESS submits → Admin rejects with comment | The second half of the core workflow; returns work to the employee. No workaround. |
| TC-200 | ESS cannot access the supervisor view | Access-control boundary; a leak lets an ESS action others' timesheets — security/compliance. |
| TC-202 | Owner cannot Approve/Reject their own timesheet | Segregation-of-duties; self-approval would be a compliance breach. |

## P1 — High impact (primary path, high reach, audit)

| ID | Scenario | Rationale |
|---|---|---|
| TC-003 | ESS adds a row, Save toast, Submit | The ESS-submit half is on every lifecycle; high reach; confirms the `Successfully Saved` contract. |
| TC-004 | Action log captures both roles (audit trail) | Auditability of who submitted/approved — key compliance expectation. |
| TC-100 | Supervisor sees Approve/Reject only when Submitted | Guards the state machine at the UI on the common path. |
| TC-201 | My Timesheet is self-scoped (ESS) | Confirms the ESS can only submit their own — high-reach scoping guarantee. |
| TC-500 | State badge transitions across the journey | The visible proof of each lifecycle transition; high-impact rendering. |

## P2 — Moderate (secondary flows, edges of common path, workaround exists)

| TC-402 | Empty timesheet submitted then approved | Zero-hour edge of the journey. |

## Notes for `/generate-tests`
- **P0 + P1 = 9 scenarios (< 12)** → per the generate-tests rule, the suite includes **P0 + P1 + P2**.
  P2 adds 7 → a target of **~12–14 E2E tests** (some UI-State items, TC-500/501/502, fold into the journey
  tests rather than spawning separate specs, so the written count lands around 12).
- These are **expensive** two-session journeys (ESS UI submit + role hand-off + supervisor UI action) —
  each test seeds a fresh, isolated week for the ESS employee (timesheets are one-per-week & undeletable).
- Setup (beforeAll, admin API): a dedicated ESS employee + login (`userRoleId: 2`) reporting to the session
  admin, plus a stable create-if-absent Customer→Project→Activity. **Verify in Step 4** the seeded project
  is visible in the ESS project autocomplete; if not, add the ESS as a project admin.
