# Test Strategy — Time → Project Report

> Input: `docs/test-scenarios_Time -> Project Report.md` (37 scenarios). Feature: **Time → Reports → Project Report**.
> Generated by `/test-strategy`. Consumed by `/define-priority`.
>
> **Framework reality:** executable layers are **E2E** (`chromium`, `tests/**`) and **API**
> (`api`, `tests/api/**`) only — no component/unit harness. "Component"/"Unit" are conceptual and fold up to E2E/API.
>
> **Reuse / new:** this is a **read-only reporting** feature (no CRUD). Existing support exists for the
> *data backbone* — `src/api/orangehrmOSAPI/TimeProjectsApi.ts` (projects/customers), `TimesheetsApi.ts`
> (create/fill/submit/approve timesheets) — but there is **no `ProjectReportPage`** and no report-data API
> wrapper yet. New artifacts needed: `src/pages/time/ProjectReportPage.ts` (criteria card + results table +
> drill-down) and a thin `TimeReportsApi` (or extend `TimeProjectsApi`) for `GET /time/reports/data`.
> It follows the read/assert patterns of the Attendance report-style suites rather than the CRUD suites.

## 1. Distribution

| Layer | Count | Focus | Est. time |
|---|---|---|---|
| **E2E** | 22 | Criteria form (required Project Name, autocomplete, date range, approved toggle, collapse), View → results table, columns, Total Duration footer, activity drill-down, empty-state, `(N) Record(s) Found`, re-run refresh, unauth redirect | ~6–9 min |
| **API** | 15 | `/time/reports/data` contract: per-activity aggregation, `includeTimesheet=all\|onlyApproved` filtering, date-range filtering, `meta.sum`/`meta.total`, drill-down (`displayProjectActivityDetailsReport`) totals, authorization/`onlyAllowed` scoping, pagination, invalid projectId | ~1–2 min |
| **Component** | 0 (→ E2E) | OXD collapsible card / table / autocomplete rendering — no mount harness | — |
| **Unit** | 0 | No isolated client logic; hour summation lives server-side | — |

> This feature **reads aggregated timesheet data**; it does not mutate. The expensive part is **data setup**:
> a project + activities + filled, submitted, and approved timesheet rows must exist so totals are deterministic.
> Build that **once via API** (`TimeProjectsApi` + `TimesheetsApi`) in `beforeAll`, then assert the report.

## 3. Decision Rationale (contested assignments)

- **TC-101/102/103/105 → API primary.** These are *arithmetic/filtering* facts about how hours are summed and
  which approval states/dates are included. They are exact and fast against `/time/reports/data` and free of
  render noise; the UI only needs to show *a* number (covered at TC-003/007). The `includeTimesheet=all` vs
  `onlyApproved` difference was already verified live (96.00 vs 48.00) — the API test pins that delta.
- **TC-004/104 → E2E primary.** The activity drill-down is a *navigation + new table* interaction
  (`displayProjectActivityDetailsReport`) only the browser exercises; API double-checks that the per-employee
  rows reconcile to the parent activity total.
- **TC-100/300/301/303 → E2E.** Required-field and autocomplete-resolution behaviour is user-facing inline
  validation — must be seen in the browser.
- **TC-202/203/304 → API only.** Authorization on the data endpoint, `onlyAllowed` project scoping, and
  invalid-id handling have no UI surface beyond the access/empty states already covered.
- **TC-401/404 → API.** Out-of-range emptiness (verified) and >50-row pagination are impractical/slow via UI.
- **Data setup (the backbone):** seed a dedicated project + ≥1 activity, then create a timesheet for a known
  employee, fill rows, **submit and approve some / leave some submitted**, so that `all` > `onlyApproved` is
  deterministic. Do this via `TimeProjectsApi`/`TimesheetsApi` in `beforeAll`; use **unique names**
  (`Date.now()`); never assert absolute totals against pre-existing instance data — assert the **delta** the
  test itself created (relative/known-project assertions only).

## 4. Anti-Patterns Found in Existing Tests
1. **Folded scenarios** (one test covering many TCs) seen in some Admin/Attendance suites — forbidden by
   `generate-tests`. Project Report keeps **one test per scenario**.
2. **Asserting absolute totals** against shared instance data would be flaky — the instance already has 15
   projects with assorted hours. Mitigation: each test seeds or targets a **known project** and asserts its own
   numbers (or relative comparisons `onlyApproved ≤ all`).
3. **Validation tested at E2E that belongs at API** — kept out: approval/date-filtering math is assigned to API
   (TC-101/102/105), only the *affordance* (a number, "Required", empty state) is E2E.
4. No existing Project Report coverage at all — this strategy establishes the `ProjectReportPage` + reports-data
   API wrapper.
