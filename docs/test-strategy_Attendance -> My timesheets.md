# Test Strategy — Attendance → My Timesheets

> Input: `docs/test-scenarios_Attendance -> My timesheets.md` (53 scenarios).
> Generated by `/test-strategy`. Consumed by `/define-priority`.
>
> **Framework reality:** executable layers are **E2E** (`chromium`, `tests/**`) and **API**
> (`api`, `tests/api/**`) only — there is no component/unit mount harness for the Vue/OXD front-end.
> "Component"/"Unit" below are conceptual; everything that runs maps to **E2E** or **API**.
>
> **Reuse:** `TimeProjectsApi` + `test-data/time/frontend/projects.ts` already cover Customer/Project
> creation; this feature **extends** them with an **Activity** create helper, adds a new **`TimesheetsApi`**
> (default/create/entries/submit/action-logs), a new **`MyTimesheetPage`** POM + fixture, and
> `test-data/time/frontend/timesheets.ts`. Session/bootstrap login reuses `OrangehrmAdminApi`.

## 1. Distribution

| Layer | Count | Focus | Est. time |
|---|---|---|---|
| **E2E** | 46 | Period navigation, Create → Edit (row add/edit/delete) → Save → Submit journeys, OXD hours validation, button/status/empty UI states, autocomplete + activity scoping, self-scope, auth redirect | ~12–18 min |
| **API** | 7 | State machine + `allowedActions`, one-per-week uniqueness, day-column/workweek structure, cross-employee authorization (read & write), re-submit guard, year-boundary dates | ~1–2 min |
| **Component** | 0 (→ E2E) | OXD grid/row/select rendering — no mount harness | — |
| **Unit** | 0 | Hour parsing + total aggregation are server-computed (`meta.sum`/`meta.columns`) → exercised via API | — |

> Defense-in-depth cases (totals, submit transition, self-scope) are counted once at their **primary**
> layer and carry a noted **secondary** layer.

This feature is **write-heavy** (a multi-step Create→Edit→Save→Submit lifecycle), the opposite of the
read-only My Records screen — so the centre of gravity is genuinely E2E, while the **state machine and
authorization contracts** are cheapest and most precise at API.

## 3. Decision Rationale (contested assignments)

- **TC-100 / TC-104 / TC-305 (state machine) → API.** Uniqueness, the `NOT_SUBMITTED→SUBMITTED`
  transition, the disappearance of `SUBMIT` from `allowedActions`, and the re-submit guard are all
  contract-level facts. Asserting them on the JSON (`/timesheets/default`, `/{id}/entries` `meta`,
  `PUT /{id}`) is precise and render-free; the UI sides (status text, button hidden) are covered by
  TC-006/TC-501/TC-503 already.
- **TC-101 / TC-405 (date columns) → API.** The seven day-keys and their crossing of month/year
  boundaries come straight from `meta.dates`; checking them at API avoids screenshotting headers and is
  deterministic regardless of the run date.
- **TC-203 / TC-306 (cross-employee) → API only.** "Can an ESS read/write another employee's timesheet?"
  has no UI path (no employee selector); these are pure authorization-contract tests. TC-202 keeps the
  *UI* IDOR check (deep-linking `editTimesheet/{otherId}`).
- **TC-300–304 (hours validation) → E2E.** The rule surfaces as an **OXD inline message**
  ("Should Be Less Than 24 and in HH:MM or Decimal Format") rendered client-side before any request;
  the natural assertion is on that affordance. (No separate server-validation endpoint is exposed to
  test in isolation.)
- **TC-102 / TC-403 (totals & normalisation) → E2E primary, API secondary.** The number the user trusts
  is the *rendered* one, so the primary assertion compares the DOM total to the API's
  `meta.sum.label`/persisted `duration` fetched in the same test.
- **Data dependency (affects every data-bearing case):** a row needs an active **Project + Activity**, and
  a project needs a **Customer**. A clean instance has **zero** projects. Strategy: a `beforeAll`/setup
  seeds **Customer → Project (projectAdmin = session employee) → Activity** via API and tears them down
  in cleanup; the project name is uniquified per-run to stay idempotent.
- **Timesheet seeding constraint:** **future** weeks can't be created (Create disabled), and the current
  week may already be `Submitted`. Data-bearing edit/submit tests therefore operate on a **past week**
  (Create enabled) created fresh via `POST …/timesheets {date}`, keeping each test self-contained and
  order-independent.

## 4. Anti-Patterns Avoided / Found

1. **No folded scenarios.** One `test()` per TC (the `generate-tests` skill forbids many-asserts-one-test).
2. **No validation-at-E2E-only drift _for server rules_:** state transitions and authorization are pushed
   to API; only the genuinely client-side OXD hours validation stays at E2E (it has no lower harness).
3. **No absolute, un-seeded assertions:** totals are asserted against the same-test API contract, not
   hard-coded numbers; timesheets/projects are seeded per-run and uniquified, never assuming demo data.
4. **No reliance on `current week` state** (it can be pre-submitted) — data tests use a freshly created
   past week.

## 5. Critical Flows Requiring E2E (non-negotiable)
- Create → add row → Save → Submit (the end-to-end lifecycle): **TC-004, TC-005, TC-006**.
- Hours validation guard (the most common user error): **TC-300**.
- Self-scope + auth (privacy/authorization): **TC-200, TC-204**; IDOR via UI **TC-202**.
- No-timesheet and status/button states (states every user hits): **TC-500, TC-501**.
