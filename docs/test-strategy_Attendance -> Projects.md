# Test Strategy — Attendance → Projects

> Input: `docs/test-scenarios_Attendance -> Projects.md` (35 scenarios). Feature: **Time → Project Info → Projects**.
> Generated by `/test-strategy`. Consumed by `/define-priority`.
>
> **Framework reality:** executable layers are **E2E** (`chromium`, `tests/**`) and **API**
> (`api`, `tests/api/**`) only — no component/unit harness. "Component"/"Unit" are conceptual.
>
> **Reuse / new:** no existing Projects support in the framework. This feature needs a new
> `ProjectsPage` (list + add/edit) and a `TimeProjectsApi` (projects + customers seed/cleanup) plus
> `test-data/time/frontend/projects.ts`. It follows the established CRUD patterns from
> `tests/admin/add-work-shift.spec.ts` (list/add/delete/duplicate/ESS) and the Attendance suites.

---

## 1. Distribution

| Layer | Count | Focus | Est. time |
|---|---|---|---|
| **E2E** | 24 | Add (incl. inline customer), list/columns, edit, delete+confirm, search, required/duplicate validation, activities, admin-only access, XSS render | ~6–9 min |
| **API** | 11 | `projects`/`customers` GET/POST/DELETE contracts: customer relationship, count, project-admins list, authorization (ESS 403), pagination, customer lifecycle | ~1–2 min |
| **Component** | 0 (→ E2E) | OXD list/form/modal rendering — no mount harness | — |
| **Unit** | 0 | No client logic to unit-test | — |

> Defense-in-depth (count, customer relationship, authorization) counted once at the primary layer with a
> secondary noted. CRUD that mutates shared data is seeded + cleaned per suite (unique names + API cleanup).

This is a **CRUD + dependency** feature: a project needs a **customer**, so data setup (seed a customer, and
usually a project) is the backbone — cheapest via API in hooks, with the create/list/delete journeys at E2E.

## 3. Decision Rationale (contested assignments)

- **TC-005 (inline customer) → E2E.** The modal create + auto-select-into-the-parent-field is a UI
  interaction that only the browser exercises; the customer POST is covered by API setup elsewhere.
- **TC-102/303 (duplicate name) → E2E primary.** OrangeHRM uniqueness errors are surfaced inline; the exact
  copy ("Already exists" — to be confirmed live) and that no row is created are user-facing → E2E, with the
  contract (no duplicate row) double-checked via API.
- **TC-103/106 → API.** Project↔customer linkage and "customer survives project deletion" are data-lifecycle
  facts — precise and fast at the contract, free of render noise.
- **TC-202 → API only.** ESS-forbidden POST has no UI path beyond the "Credential Required" page (TC-200/203).
- **TC-400/402 → API.** Length boundary and >50 pagination are impractical/slow to build through the UI.
- **Data setup:** a project requires a **customer**. Seed a customer (and, for read/delete tests, a project)
  via `TimeProjectsApi` in `beforeAll`/`beforeEach`; use **unique names** (`Date.now()`), capture created ids,
  and **hard-delete in `afterAll`** (`DELETE /time/projects {ids}` / `…/customers {ids}`) — the work-shift
  cleanup pattern. Never assert absolute totals; assert by unique name / relative count.

## 4. Anti-Patterns Found in Existing Tests
1. **Folded scenarios** in `tests/admin/add-work-shift.spec.ts` (one test, many TCs) — forbidden by
   `generate-tests`. Projects keeps **one test per scenario**.
2. **Leftover data** is the risk for a CRUD feature with no cleanup. Mitigation: API hard-delete in `afterAll`
   keyed on created ids, plus unique names. (Note: an exploration-created customer "PIO Explore Customer" may
   persist on the instance — tests must not assume a clean customer table; key off their own seeded names.)
3. No existing Projects/Customers coverage at all — this strategy establishes it (TC-001/004/200).

## 5. Critical Flows Requiring E2E (non-negotiable)
- Add (with customer) → list, and delete + confirm: **TC-001, TC-004**.
- Required-field + duplicate validation on the add form: **TC-100, TC-101, TC-303**.
- Admin-only access + unauthenticated redirect: **TC-200, TC-201**.
