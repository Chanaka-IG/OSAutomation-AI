## Context

Employment Status is a **single-field CRUD master-data feature** feeding the PIM Job Details
`empStatusId` dropdown. It is the simplest shape in the Admin → Job family: one `Name` field, no
sub-grids (unlike Pay Grades' Currencies), and a **Save → redirect-to-list** choreography (like Job
Titles, NOT like Pay Grades which redirects to its edit page).

The entire risk surface is:

1. **The record-level `Name` contract** — live async validation (`Required`, `Already exists`,
   `Should not exceed 50 characters` — all fire while typing), mirrored server-side by
   `POST /api/v2/admin/employment-statuses { name }` → 422 on violation.
2. **Admin-only RBAC** — the page and API must reject ESS and unauthenticated callers.
3. **FK-protected delete** — `DELETE /api/v2/admin/employment-statuses { ids }` is blocked with
   `"This record is in use and cannot be deleted"` when an employee references the status.

Because there is no nested sub-resource and no browser-only UX beyond the inline validation and the
delete dialog, this feature is **API-heavy**: the validation contracts, uniqueness, boundaries, and
RBAC are all cheaper and more deterministic at the API layer. The browser layer carries only what is
genuinely visual/journey-shaped: the live "while-typing" validation, the create→redirect→list
journey, the XSS render proof, ESS lockout, and the delete confirmation dialog.

No Unit/Component layers — deployed black-box app; OXD form components are upstream-tested (same
rationale as the Job Title, Pay Grades, Dashboard, and Leave strategies). The "Component" scenarios
(TC-101/103/503/501) fold into one combined E2E validation journey rather than standing up a
component harness.

**Framework note**: `EmploymentStatusesApi` already exists (`getAll`, `getIdByName`,
`createIfAbsent`, `create`) but has **no `delete` method**. Add
`deleteByIds(ids: number[])` (DELETE `/api/v2/admin/employment-statuses { ids }`) mirroring
`JobTitlesApi.deleteByIds`, for suite cleanup. There is **no frontend test-data file** for this
feature yet — `generate-tests` should add `test-data/admin/frontend/employmentStatus.ts`
(selectors, URLs, validation copy, seeded names) following `adminPayGrades`/`adminJobTitles`, plus a
small `EmploymentStatusPage` POM (or reuse the Job Titles list/add pattern). The 4 seeded statuses
(`Permanent`, `Probation`, `Intern`, `Terminated`) are **master data** verified by `tests/setup`;
tests must create their own timestamped statuses (`MES-<ts>`) and clean up — never mutate or delete
the seeded four.

## Contested Assignments — Rationale

- **TC-102 stays E2E** even though uniqueness is also API-tested (TC-303): the live, debounced,
  pre-save inline `Already exists` is frontend behavior with real flake potential and is unseeable at
  the API layer. The API test guards the contract; the E2E test guards the UX.
- **TC-103/302 (length boundary) split**: the UI message (`Should not exceed 50 characters`) is
  asserted once in the combined validation test; the exact 50/51 boundary is a server contract
  (TC-104 = 50 ok, TC-302 = 51 → 422). ⚠ The limit is **50** (Pay Grades parity), NOT Job Titles' 100.
- **Create assertion is "redirect to LIST"** — unlike Pay Grades (redirect to edit page). Older
  Pay-Grades "assert on edit URL" patterns do **not** apply; this matches Job Titles.
- **TC-105 (in-use delete) is API-only and read-only**: it must NOT actually delete a seeded status.
  Assert the block (error response / status still present via GET) against an in-use seeded id; an
  E2E version would risk mutating master data and is not worth the flake.
- **TC-204 (XSS) stays E2E**: "stored inert" is only provable in a rendering DOM.
- **TC-005 (propagation to PIM Job Details) deferred to one optional smoke**: surfaces only in
  PIM → employee → Job tab dropdown, requiring an employee fixture; lower impact, kept optional and
  not a release gate (the API GET reflecting the new id is the cheap proof).

## Anti-Patterns Found in Existing Tests / Avoided Here

- `EmploymentStatusesApi` has **no delete** method — add `deleteByIds(ids)` (mirror
  `JobTitlesApi.deleteByIds`) rather than cleaning up via the UI in every test (UI delete belongs to
  exactly one test: TC-505).
- `tests/setup` seeds the 4 statuses via `createIfAbsent`; new tests must NOT delete or rename those
  seeded statuses — use timestamped names (`MES-<ts>`) and dedicated `afterAll` cleanup.
- Assert success via `.oxd-toast--success` (or the resulting row/redirect/counter), never the page
  heading (project memory — the list title is an `<h6>` that is identical before and after).
- Don't push input validation, uniqueness, or RBAC error codes to E2E — they belong at the API
  layer (anti-pattern: "input validation tested at E2E"). E2E keeps only the *live inline* validation
  UX, which the API cannot observe.
- Don't assert the exact `Should not exceed 50 characters` / `Already exists` strings at more than one
  layer — assert the message once (E2E) and the contract (422) once (API).
