## Context

The Dashboard is a **read-mostly aggregation page** — its risk is in rendering the right
widgets per role and wiring shortcuts/counters to the right modules. The UI layer is the
primary surface (widget visibility, navigation, empty states); the *data* rules
(aggregation counts, permission gating on the dashboard APIs) are cheaper and more
deterministic at the API layer (`/api/v2/dashboard/employees/*`, `/dashboard/shortcuts`).

No Unit/Component layers (deployed black-box app; OXD upstream-tested) — same rationale
as the Leave lifecycle strategy.

## Contested Assignments — Rationale

- **TC-102 (Employees on Leave Today) pushed to API**: today's date is uncontrollable in
  the UI (weekend runs make the positive case impossible — verified work-week rule). The
  API accepts `?date=`, so the rule is tested deterministically there; the UI widget's
  render (either list or empty text) is covered state-agnostically inside TC-001.
- **TC-301 stays E2E with route mocking**: failure isolation is a frontend behavior;
  BP §6 exists precisely for this (forcing a 500 on one widget API).
- **TC-006 is the one deliberately "heavy" E2E**: it spans Leave seeding + Dashboard +
  deep-link navigation. Kept because My Actions is the dashboard's core business value;
  seeding reuses the proven `AuthApi`/`LeaveRequestsApi` self-apply pattern from
  `leave-e2e-lifecycle.spec.ts`.

## Anti-Patterns Found in Existing Tests

- No existing dashboard suite exists; `tests/pim/login.spec.ts` asserts the post-login
  URL only. The new suite must not duplicate login-mechanics coverage — start each test
  from an authenticated session and assert dashboard-specific behavior.
- Reuse the runtime name→id resolution for leave types (instance drift, see
  `leave-e2e-lifecycle.spec.ts`) when seeding the TC-006 pending request.
