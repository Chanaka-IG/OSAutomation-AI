# Test Strategy — Attendance → Punch-In/Out

> Input: `docs/test-scenarios_Attendance -> Punch-In-Out.md` (39 scenarios).
> Generated by `/test-strategy`. Consumed by `/define-priority`.
>
> **Framework reality:** this repo ships two executable layers only — **E2E** (`chromium` project,
> `tests/**`) and **API** (`api` project, `tests/api/**`). There is **no component or unit harness**
> (the Vue OXD front-end is not unit-mounted here). So "Component" and "Unit" below are *conceptual
> recommendations* for where a rule could be pushed if infrastructure existed; every assignment that
> must actually run is mapped to **E2E** or **API**.

## 1. Distribution

| Layer | Count | Focus | Est. time |
|---|---|---|---|
| **E2E** | 24 | Punch state machine, redirects, UI affordances, render safety, My Records verification | ~6–9 min |
| **API** | 13 | Server-side invariants (single-open, overlap, ordering), config contract, timezone, payload tampering | ~1–2 min |
| **Component** | 0 (→ folded into E2E) | OXD disabled-field / button-label rendering — no mount harness | — |
| **Unit** | 0 | No pure-logic units exposed to this test project (duration math lives server-side → API) | — |

> Several scenarios are **defense-in-depth** (counted once above, in their *primary* layer, but listed
> with a secondary layer): the single-open-punch invariant, punch ordering, note-optional, timezone,
> and ESS scoping are validated at both API (contract) and E2E (user-visible behaviour).

Shape: wide-ish at API for the invariants, a deliberately fuller E2E band because this feature is a
**stateful multi-page journey** (punchIn ⇄ punchOut redirects, then My Records) that only E2E exercises end-to-end.

## 3. Decision Rationale (contested assignments)

- **TC-100 vs TC-305 (cannot punch in twice).** The *UI* enforces this by redirecting `punchIn → punchOut`, which is what a user sees → **E2E**. But a malicious client can `POST /records` directly, so the *invariant* must also be proven server-side → **TC-305 @ API**. Splitting avoids an E2E test pretending to cover a server rule it can't reach.
- **TC-300/301 (required Date/Time) kept at E2E, not pushed to API.** Normally input validation is pushed down (anti-pattern: "validation at E2E"). Here the fields are **disabled by default** — the only way a user reaches the required-error path is with config ON in the rendered OXD form, so the *user-facing* assertion is inherently E2E. The server-side format/contract is covered separately by **TC-302 @ API**.
- **TC-106 duration → API.** Duration is computed and stored server-side; asserting the float at API is deterministic, while the grid display (E2E) is a thin secondary check.
- **TC-204 → API only.** "Punch for another employee" has no UI path (no employee selector on the self-service screen); it is purely an authorization-contract test.
- **TC-403 → E2E primary.** XSS/escaping must be verified in a real DOM (no dialog fired, no live `<script>`), which only the browser provides; API only confirms the bytes are stored.
- **Config-dependent cases (TC-006/103/300/301/302/303/304/404/406)** require flipping `canUserChangeCurrentTime` on a **shared singleton** config. Strategy: prefer **API** where the rule is server-side (so no global UI state change is needed); for the few E2E ones, toggle config in `beforeAll` and **restore in `afterAll`** (same pattern as PIM Optional Fields singleton — see `[[pim-optional-fields]]`).

## 4. Anti-Patterns Found in Existing Tests

1. **`tests/admin/add-work-shift.spec.ts` folds many scenarios into one test** (e.g. `TC-ADMIN-AWS-001` "Folds TC-500 + TC-504"; `TC-002` folds TC-505/102/302). This is exactly the **"one test, many TCs"** shape the `generate-tests` skill explicitly forbids ("Creates separate, self-contained automated test cases for each prioritized test scenario… Never do as follows"). → For Punch-In/Out, write **one test per prioritized scenario** so reporting maps 1:1.
2. **`Date.now()`-based unique names** (`WS Defaults ${Date.now()}`) are used for isolation — acceptable, but ensure attendance tests likewise **never reuse another suite's data** and **clean up created records** (records can't be deleted via UI with config OFF → clean via API/admin or scope to a dedicated employee).
3. No existing attendance/time E2E coverage at all → **critical-flow gap**: the punch state machine currently has **zero** automated tests. This strategy closes the P0 gap (TC-001/003/004/100).

## 5. Critical Flows Requiring E2E (non-negotiable)
- Punch In → redirect → Punch Out → redirect (the core state machine): **TC-001, TC-003, TC-100, TC-101**.
- A completed cycle is verifiable by the employee: **TC-004**.
- Self-service scoping & admin-screen lockout: **TC-200, TC-201, TC-202**.
