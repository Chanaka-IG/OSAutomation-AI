## `tests/time/employee-timesheets.spec.ts`

### What's Good
- **Locators live only in the POM**; the spec holds assertions only — complies with best-practices §2 ("Locators should always be defined in the page class") and §4 ("keep `expect` in the spec").
- **Self-contained tests** (login → seed → act → assert) with fresh, isolated past weeks per mutating test (`nextFreshWeek`/`nextSubmittedWeek`) — no shared state, idempotent re-runs (§11 "Each test self-contained").
- **Defense-in-depth assertions**: UI state (`statusText`, `actionCardHeading`) plus the persisted API state (`meta.status.id`) — proves the outcome, not just the DOM.
- **No anti-patterns**: no `waitForTimeout`, no `test.only`, no hardcoded record IDs, no nth-child chains.
- **Domain discrepancy surfaced, not silently swallowed**: TC-ETS-300 documents that OS 5.8 accepts an empty reject comment (the domain skill's "mandatory comment" is Enterprise-only/stale), and the file header + test comment call it out (generate-tests rule: report behaviour that contradicts the domain skill).
- Uses `auth.essTestUser` + `loginWithCredentials` for the ESS-denied check — the sanctioned ESS-login pattern (best-practices §5).

### Issues Found

**[IMPORTANT] `afterAll` cleanup leaves the seeded Project/Customer behind (silent 400).**
- Lines ~119–127 (`test.afterAll`). The run logged `deleteProjects non-OK {status:400}` and `deleteCustomers non-OK {status:400}` — the project is referenced by the (undeletable) seeded timesheets, so the hard-delete is rejected and the Customer/Project linger on the shared instance.
- Best-practice violated: §8/§"Add data via APIs" — *"clean up the data after the test execution"*. Unique-per-run names (`stamp`) mean it isn't a correctness/flake risk, but residue accumulates.
- Fix: accept-and-log the project as intentionally retained (it can't be removed once timesheeted), OR reuse a single suite-owned project across runs via `ensureCustomer`/`getProjectIdByName` (create-if-absent) instead of a per-run stamped name, so nothing new accumulates. At minimum, make the retained-data outcome explicit rather than a generic `warn`.

**[SUGGESTION] `REPORTING_METHOD_DIRECT = 1` is a magic constant in the spec (line ~33).**
- Best-practice §"Pass data to Page class": configuration/data should come from test-data, not literals in the spec. Move it into `employeeTimesheets` test-data (e.g. `reportingMethodDirectId`) and reference it.

**[SUGGESTION] State seeding happens in the test body, not a hook.**
- `nextSubmittedWeek(api)` / `nextFreshWeek(api)` are called inside each test (e.g. lines ~167, ~181, ~216). Best-practice §"Add data via APIs" prefers seeding in `beforeEach`/`beforeAll`. This mirrors the approved sibling `my-timesheets.spec.ts` (each test needs a *distinct* fresh week, which a shared hook can't provide), so it is acceptable — but worth a short inline note that the in-body seeding is deliberate for per-week isolation.

**[SUGGESTION] TC-ETS-201 asserts only the heading.**
- Line ~256. Could also assert `await expect(page).toHaveURL(etsData.urlPatterns.detail)` for parity with TC-ETS-002, strengthening "admin reached the employee's detail page".
