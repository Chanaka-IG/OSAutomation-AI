# Test Strategy — Attendance → My Records

> Input: `docs/test-scenarios_Attendance -> My Records.md` (34 scenarios).
> Generated by `/test-strategy`. Consumed by `/define-priority`.
>
> **Framework reality:** executable layers are **E2E** (`chromium`, `tests/**`) and **API**
> (`api`, `tests/api/**`) only — no component/unit harness for the Vue OXD front-end. "Component"/"Unit"
> below are conceptual; everything that runs maps to **E2E** or **API**.
>
> **Reuse:** the prior pipeline built `MyAttendanceRecordsPage`, `AttendanceApi`, and
> `test-data/time/frontend/attendance.ts`. This feature extends those (date-filter methods, a
> `getRecordsByDate` reader) rather than starting fresh.

This feature is **read-heavy**: the bulk is "set a date → fire one GET → assert the rendered table",
which is genuinely E2E, while the aggregation/scoping *contract* is cheapest and most precise at API.

## 3. Decision Rationale (contested assignments)

- **TC-100 (userDate filtering) → API.** Whether a record buckets under its *local* date or its *UTC* date
  is an offset-sensitive rule; an API assertion (seed at a known offset, query the date) is precise and
  free of render noise. The E2E side is already covered incidentally by TC-002/003.
- **TC-004/005 (total & count) → E2E primary, API secondary.** The number the user trusts is the *rendered*
  one, so the primary assertion compares the DOM to the API's `meta.sum.label`/`meta.total` (fetched in the
  same test) — proving the UI faithfully reflects the contract. Pure aggregation correctness is the API leg.
- **TC-400 (pagination) → API only.** Creating >50 records through the UI is slow and brittle; the `limit`/
  `offset` behaviour is a contract concern. (If the UI has no pager, the API test documents the cap and the
  strategy flags it — see §"no silent caps".)
- **TC-204 → API only.** "Can I read another employee's records?" has no UI path (no selector); it is a pure
  authorization-contract test.
- **Seeding constraint (affects nearly every data-bearing case):** the server **rejects explicit past/future
  punch dates** while `canUserChangeCurrentTime=false` (`400 "Provided Date And Time Invalid"`). Therefore
  records can only be seeded at *current* server time (→ **today**). Strategy:
  - data-bearing tests seed cycles for **today** via `AttendanceApi` and assert on **unique notes** + **relative
    counts** (count-before vs count-after), never absolute totals;
  - the **empty-state** path uses a **far-past date** (always empty; viewing any date is allowed);
  - this avoids toggling the global config singleton, keeping the suite side-effect-free.

## 4. Anti-Patterns Found in Existing Tests

1. **Folded scenarios** persist in `tests/admin/add-work-shift.spec.ts` (one test asserts many TCs) — the
   `generate-tests` skill forbids it. My Records will keep **one test per scenario**.
2. **Records are not cleanable** under default config (no UI delete, API delete not exposed) — so absolute
   record counts are a flakiness trap. Mitigation baked into §3: unique notes + relative counts + far-past
   empty date. `tests/attendance/punch-in-out.spec.ts` already follows this; My Records will too.
3. No existing coverage of the **date filter / aggregation** path — this strategy closes that gap (TC-002/004/005/300/500).
