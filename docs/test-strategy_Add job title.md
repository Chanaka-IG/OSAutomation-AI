## Context

Add Job Title is a **small CRUD form feeding master data** to PIM, Recruitment, and
Performance. Its risk concentrates in three places: (1) the live, async client-side
validation (Required / length / duplicate fire while typing), (2) server-side parity for
those same rules (`POST /api/v2/admin/job-titles` → 422 `Invalid Parameter`), and
(3) the verified **silent-failure gap** — a padded duplicate bypasses the client check,
422s on the server, and the UI navigates back with no toast.

The form-contract rules are cheap and deterministic at the **API layer**; the inline
validation UX, the file chooser, and the toast/redirect choreography only exist in the
**browser**. No Unit/Component layers — deployed black-box app, OXD components are
upstream-tested (same rationale as the Dashboard and Leave strategies). Component-ish
scenarios (TC-101/104/301/502) fold into one combined E2E validation journey rather
than standing up a component harness for a single form.

**Framework note**: `JobTitlesApi` already exists (`getAll`, `getIdByTitle`, `create`,
`createIfAbsent`) and the 6 seeded titles are **master data consumed by other suites**
(KPIs, vacancies) — tests must create their own timestamped titles and clean up via
`DELETE /api/v2/admin/job-titles { ids }` (method to be added to `JobTitlesApi`).

## Contested Assignments — Rationale

- **TC-102/103 stay E2E** even though uniqueness is also API-tested (TC-305): the *live,
  debounced, pre-save* inline error is frontend behavior with real flake potential — it is
  the thing a regression would break, and the API layer cannot see it.
- **TC-303 pushed to API**: the interesting half (422 + no record) is a server contract.
  The UI half ("no toast appears") would mean asserting the *absence* of UX that *should*
  exist per business-rules §10 — pinned as an API invariant + documented app-bug note
  instead of encoding the buggy UX as an E2E expectation.
- **TC-105/304 (length boundary) at API, not UI**: the UI blocks typing past the error
  state identically at 101 and 120 chars (verified live at 120); the exact boundary is a
  server contract. The UI message itself is covered once in the combined validation test.
- **TC-004 kept as one E2E smoke** despite being API-verifiable: a master-data record
  that doesn't surface in dependent dropdowns is the highest-impact failure mode of this
  feature (blocks vacancy creation), worth one cross-module UI assertion.
- **TC-204 (XSS) stays E2E**: "stored inert" is only provable in a rendering DOM —
  an API test would just prove storage, not non-execution.

## Anti-Patterns Found in Existing Tests

- `tests/setup` master-data verification seeds the 6 job titles via `createIfAbsent` —
  new tests must NOT delete or rename those titles (KPI/vacancy suites reference them);
  use timestamped titles (`AJT-<ts>`) and dedicated cleanup.
- `JobTitlesApi` has no `delete` method — add `deleteByIds(ids: number[])` rather than
  cleaning up through the UI in every test (UI delete belongs to exactly one test: TC-505).
- Several older suites assert success via page headings; per project memory and
  business-rules §10, assert `.oxd-toast--success` (or the row itself) — toasts
  auto-dismiss in ~3s, so assert toast *before* list assertions.
