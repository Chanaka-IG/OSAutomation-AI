# Test Scenarios: E2E Leave Lifecycle — Add Entitlement → Assign to ESS → Apply as ESS → Action as Admin/Supervisor

> Feature: The **full cross-role leave journey** chained end-to-end:
> 1. **Admin adds a leave entitlement** (`Leave → Entitlements → Add Entitlements`, `/leave/addLeaveEntitlement`) for an ESS employee (individual and bulk modes).
> 2. **ESS employee sees the entitlement/balance** and **applies for leave** (`/leave/applyLeave`) → request enters **Pending Approval**.
> 3. **Admin or Supervisor actions the request** from the Leave List (`/leave/viewLeaveList`): **Approve / Reject / Cancel**, with balance-escrow verification at every transition.
>
> Source: `orangehrm-opensource-domain` skill (business-rules.md §4 Leave Workflow, §5 Leave Types & Entitlements, §6 Assign leaves; user-flows.md Flow 4, Flow 10), plus verified behaviors from existing suites (`tests/leave/*.spec.ts`).
> Generated by `create-scenarios` skill.

## Context & Key Domain Rules

- **Entitlement is the gate**: without an entitlement for a leave type, the ESS Apply Leave dropdown **does not even list that type** (verified behavior — there is no "0.00 balance" error path from the dropdown; the type is simply absent).
- **Balance formula**: `balance = entitlement − (pending + scheduled + taken)`. Pending days are **escrowed at submission**, not at approval.
- **Status codes** (DB / API): `-1 Rejected, 0 Cancelled, 1 Pending Approval, 2 Scheduled, 3 Taken`.
- **ESS-applied leave → Pending Approval (1)**; Admin-*assigned* leave → Scheduled (2). To produce a Pending request for the action phase, the **employee must self-apply**.
- **Escrow math on actions**: Approve keeps days consumed (balance delta 0); Reject/Cancel release them (delta +days).
- **Overlapping leave** on ESS Apply is surfaced as an inline **"(N) Record Found" conflict panel**, not a toast.
- Admin can action **any** employee's request; a Supervisor only their **subordinates'**. **Self-approval is blocked**.
- Leave List actions (Approve/Reject inline buttons, ⋮ → Cancel Leave) are **immediate — no confirmation modal** — and fire `.oxd-toast--success`.
- Entitlement form: Employee autocomplete (individual mode), Leave Type dropdown, Leave Period, Entitlement number. Saving shows a **confirmation dialog when updating an existing entitlement** (old → new value).
- Leave Period default: `2026-01-01 – 2026-12-31`. Known seeded data: **2026-08-06 is a global holiday** (avoid; single-day requests there fail with "No Working Days Selected").
- API endpoints: `POST /api/v2/leave/leave-entitlements`, `POST /api/v2/leave/leave-requests` (self-apply), `PUT /api/v2/leave/employees/leave-requests/{id}` `{action}`, `GET /api/v2/leave/employees/{empNumber}/leave-entitlements` (balance).

## Happy Path (TC-001–099)

### TC-001: Full golden path — entitlement → apply → approve
**Category**: Happy Path
**Preconditions**: Fresh ESS employee with user account and a supervisor; no existing entitlement for the target leave type.
**Steps**:
1. Login as Admin → `Leave → Entitlements → Add Entitlements`.
2. Individual mode: pick the ESS employee, leave type (e.g. Annual), current leave period, entitlement = 15.00 → Save.
3. Logout; login as the ESS employee → `/leave/applyLeave`.
4. Verify the leave type now appears in the dropdown and balance widget shows `15.00 Day(s)`.
5. Apply 2 working days (future weekdays) → Apply.
6. Logout; login as Admin → `/leave/viewLeaveList` → filter Pending Approval + employee → **Approve**.
**Expected Results**: Entitlement save toast; apply success toast; request visible in My Leave as *Pending Approval (2.00)*; after approve, success toast and status → **Scheduled**; balance stays `13.00` (escrow retained).
**Business Rule**: Entitlement gates application; Pending → Scheduled on approve; escrow retained.
**Suggested Layer**: E2E

### TC-002: Full path ending in Reject — balance released
**Category**: Happy Path
**Preconditions**: As TC-001 (separate employee/dates).
**Steps**: Entitle 10 days → ESS applies 3 days → Admin **Rejects** from Leave List.
**Expected Results**: Status → **Rejected (-1)**; employee balance returns to `10.00` (escrowed 3 days released).
**Business Rule**: Reject is terminal and releases escrowed days.
**Suggested Layer**: E2E

### TC-003: Full path ending in Cancel by Admin — balance released
**Category**: Happy Path
**Preconditions**: ESS employee with entitlement and a Pending request.
**Steps**: Admin → Leave List → row ⋮ → **Cancel Leave**.
**Expected Results**: Status → **Cancelled (0)**; balance restored to full entitlement.
**Business Rule**: Cancel is terminal and releases escrowed days.
**Suggested Layer**: E2E

### TC-004: Supervisor approves subordinate's request (instead of Admin)
**Category**: Happy Path
**Preconditions**: ESS employee reports to a Supervisor (ESS user with subordinate); Pending request exists.
**Steps**: Login as Supervisor → Leave tab → Leave List → filter Pending → **Approve** subordinate's row.
**Expected Results**: Success toast; status → **Scheduled**; verified via API status query.
**Business Rule**: Supervisors can action subordinates' requests.
**Suggested Layer**: E2E

### TC-005: Supervisor rejects subordinate's request
**Category**: Happy Path
**Preconditions**: As TC-004 with a fresh Pending request.
**Steps**: Supervisor → Leave List → **Reject**.
**Expected Results**: Status → **Rejected**; subordinate's balance released.
**Business Rule**: Supervisor reject authority over subordinates.
**Suggested Layer**: E2E

### TC-006: ESS cancels their own pending request from My Leave
**Category**: Happy Path
**Preconditions**: ESS employee with own Pending request.
**Steps**: ESS → `/leave/viewMyLeaveList` → inline **Cancel** on own row.
**Expected Results**: Success toast; status → **Cancelled**; balance released.
**Business Rule**: Employees may cancel their own pending leave.
**Suggested Layer**: E2E

### TC-007: Update (increase) an existing entitlement — confirmation dialog
**Category**: Happy Path
**Preconditions**: Employee already has 15.00 entitlement for the type/period.
**Steps**: Admin → Add Entitlements → same employee/type/period, entitlement = 20.00 → Save → confirm the "updating entitlement" dialog.
**Expected Results**: Confirmation dialog shows old/new values; after confirm, success toast; Entitlements list shows 20.00; ESS balance reflects 20.00 minus any consumed days.
**Business Rule**: Re-adding for same employee/type/period updates, with explicit confirmation.
**Suggested Layer**: E2E

### TC-008: Bulk-assign entitlement to multiple employees (Multiple Employees mode)
**Category**: Happy Path
**Preconditions**: ≥2 employees in a known Sub Unit/Location.
**Steps**: Admin → Add Entitlements → toggle **Multiple Employees** → filter by Sub Unit → leave type + period + 5.00 → Save → confirm affected-count modal.
**Expected Results**: Confirmation modal states affected employee count; success toast; each affected employee's entitlement list shows 5.00.
**Business Rule**: Bulk Assign pushes the same entitlement by Location/Subunit filter (Flow 10).
**Suggested Layer**: E2E

## Business Rules (TC-100–199)

### TC-100: Leave type absent from ESS Apply dropdown without entitlement

**Steps**: ESS → `/leave/applyLeave` → open Leave Type dropdown.
**Expected Results**: Type Y is listed; type X is **not an option** at all.
**Business Rule**: Apply dropdown lists only entitled types (verified behavior; stronger than "balance 0 error").
**Suggested Layer**: E2E

### TC-101: Balance escrow on application (before any action)
**Category**: Business Rule
**Preconditions**: Employee entitled 10 days, no leave taken.
**Steps**: ESS applies 4 working days → query entitlement-balance API before/after.
**Expected Results**: Balance drops 10.00 → 6.00 immediately on submission (status still Pending).
**Business Rule**: Pending days are escrowed at submission, not at approval.
**Suggested Layer**: API

### TC-102: Approve keeps escrow (balance delta 0)
**Category**: Business Rule
**Preconditions**: Pending request of N days, balance already reduced by N.
**Steps**: Admin approves → re-query balance.
**Expected Results**: Balance unchanged by the approval; request Scheduled.
**Business Rule**: Approve converts escrow to scheduled consumption.
**Suggested Layer**: API

### TC-103: Reject/Cancel restore balance (+N days)
**Category**: Business Rule
**Preconditions**: Two Pending requests of known sizes for the same employee.
**Steps**: Admin rejects one and cancels the other → re-query balance after each.
**Expected Results**: Each action adds the request's days back to the balance.
**Business Rule**: Terminal off-ramps release escrow.
**Suggested Layer**: API

### TC-104: Over-balance application is blocked
**Category**: Business Rule
**Preconditions**: Employee entitled 2 days only.
**Steps**: ESS attempts a 5-working-day application → Apply.
**Expected Results**: No request is created — entitlement-balance API delta = 0 and no new Pending record (do not rely on the flaky "Balance not sufficient" widget text).
**Business Rule**: Cannot apply beyond available balance.
**Suggested Layer**: E2E

### TC-105: Weekend days excluded from numberOfDays
**Category**: Business Rule
**Preconditions**: Entitled employee; default Mon–Fri work week.
**Steps**: ESS applies Fri → Mon (4 calendar days).
**Expected Results**: Request consumes **2** days (Fri + Mon); balance delta = −2.
**Business Rule**: numberOfDays excludes non-working days per Work Week.
**Suggested Layer**: API

### TC-106: Scheduled request can only be Cancelled (no re-approve)

**Steps**: Query `allowedActions` via API; check Leave List row controls.
**Expected Results**: allowedActions = [CANCEL]; no Approve/Reject buttons on the row.
**Business Rule**: Scheduled → only Cancel remains.

### TC-107: Rejected/Cancelled are terminal — no further actions
**Category**: Business Rule
**Preconditions**: One Rejected and one Cancelled request.
**Steps**: Query allowedActions; attempt `PUT … {action:"APPROVE"}` on each via API.
**Expected Results**: allowedActions = []; the PUT returns 4xx (e.g. 400/422), status unchanged.

### TC-108: Self-approval blocked — supervisor cannot approve own leave
**Category**: Business Rule
**Preconditions**: Supervisor (ESS w/ subordinates) has own Pending request.
**Steps**: Supervisor → Leave List → search own pending request; also check `/leave/viewMyLeaveList` row controls.

### TC-109: Entitlement scoped to leave period — application outside period blocked
**Category**: Business Rule
**Preconditions**: Entitlement only for current period (2026-01-01–2026-12-31).
**Steps**: ESS attempts to apply for dates in the next period (e.g. 2027-02-x).

## Security (TC-200–299)

### TC-200: ESS cannot reach Add Entitlements page
**Category**: Security
**Preconditions**: Logged in as plain ESS user.
**Steps**: Direct-navigate to `/leave/addLeaveEntitlement`.
**Expected Results**: Forbidden/credentials-required page or redirect; no entitlement form rendered; Entitlements menu item absent from Leave top bar.
**Business Rule**: Entitlement management is Admin-only.
**Suggested Layer**: E2E

### TC-201: ESS cannot create entitlements via API
**Category**: Security
**Preconditions**: ESS session cookie.
**Steps**: `POST /api/v2/leave/leave-entitlements` for own empNumber with ESS session.
**Expected Results**: 403 Forbidden; no entitlement created.
**Business Rule**: Data-group permission enforcement at API layer.
**Suggested Layer**: API

### TC-202: ESS cannot action another employee's leave request via API
**Category**: Security
**Preconditions**: Pending request belonging to employee B; ESS session for employee A.
**Steps**: `PUT /api/v2/leave/employees/leave-requests/{B-id}` `{action:"APPROVE"}` as A.
**Expected Results**: 403; B's request remains Pending.
**Business Rule**: Only Admin/Supervisor-of-employee can action requests.
**Suggested Layer**: API

### TC-203: Supervisor cannot action a non-subordinate's request
**Category**: Security
**Preconditions**: Supervisor S; employee C not in S's reporting chain has a Pending request.
**Steps**: S → Leave List → search C / query API for C's requests; attempt PUT action on C's request id.
**Expected Results**: C's request not visible/actionable in UI; API action returns 403.
**Business Rule**: Supervisor scope limited to subordinates.
**Suggested Layer**: API

### TC-204: ESS cannot apply leave on behalf of another employee
**Category**: Security
**Preconditions**: ESS session for employee A.
**Steps**: `POST /api/v2/leave/leave-requests` — note endpoint is self-scoped; attempt to spoof by posting to admin assign endpoint `/api/v2/leave/employees/leave-requests` with B's empNumber.
**Expected Results**: 403 (admin assign endpoint denied for ESS); self endpoint creates only for self.
**Business Rule**: Apply endpoint is self-scoped; assign is privileged.
**Suggested Layer**: API
