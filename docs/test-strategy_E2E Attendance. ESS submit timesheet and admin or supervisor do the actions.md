# Test Strategy — E2E Attendance: ESS submits, Admin/Supervisor actions

> Input: `docs/test-scenarios_E2E Attendance. ESS submit timesheet and admin or supervisor do the actions.md` (22 scenarios).
> Generated by `/test-strategy`. Consumed by `/define-priority`.

The feature **is** a cross-role, multi-page journey: its whole value is that an ESS submits in the browser
and a *different* user actions it in the browser, with state propagating between two screens and two
sessions. That is the textbook case for **E2E** — you cannot prove the hand-off at a lower layer. So the
pyramid here is intentionally **E2E-heavy at the top for the journeys**, with an **API base** for the
state-machine guards, authz, and report-feed contracts that don't need a browser. There is **no
feature-owned pure logic or isolated component** → **no Unit/Component** tests.

Each E2E test that drives the journey **also asserts its post-condition via the employee-scoped API**
(the established `my-timesheets` / `employee-timesheets` pattern — act in the browser, confirm the
persisted state), so several "API" concerns are covered inside E2E for defense-in-depth without a second
spec.

## Layer Assignments

### E2E (14) — cross-role journeys & rendered role/state
`TC-001` (submit→approve), `TC-002` (submit→reject+comment), `TC-003` (add/save-toast/submit),
`TC-004` (two-role audit log), `TC-005` (reject→edit→resubmit→approve),
`TC-100` (no action card when not submitted), `TC-200` (ESS denied supervisor view),
`TC-201` (My Timesheet self-scoped), `TC-202` (owner can't action own),
`TC-302` (ESS hour-validation in edit), `TC-400` (reject w/o comment still rejects),
`TC-401` (multi-row totals submit→approve), `TC-500` (badge transitions), `TC-501` (buttons by role+state),
`TC-502` (action log accumulates). *(UI-State items TC-500/501/502 ride inside the journey tests; the 14
count is distinct E2E tests, not raw IDs.)*

**Rationale**: Submit and Approve/Reject only exist as rendered consequences of states reached *through the
app by two different users*. The session hand-off (ESS logout → Admin login), the disappearing Submit /
Approve buttons, the "Successfully Saved" toast, and the two-performer action log are all
DOM/navigation/session behaviours invisible to a lower layer. Access gating (`TC-200`) is the user-facing
"Credential Required" guard → E2E (the raw authz is also pinned at API in `TC-203`).

### API (8) — state machine, contracts, authz
`TC-101` (APPROVE/REJECT persisted + re-action blocked), `TC-102` ((employee,week) uniqueness),
`TC-103` (report feed), `TC-203` (ESS approve forbidden / escalation),
`TC-300` (approve a not-submitted → error), `TC-301` (re-approve → error),
plus the **post-condition assertions** backing `TC-001`/`TC-002` (verify `state==APPROVED/REJECTED` via
`GET …/employees/timesheets/{id}/entries` inside the E2E tests).

### Component (0) / Unit (0)
No feature-owned pure function or isolated component. The only client-side rule (ESS hour `< 24`) is
validated at E2E (`TC-302`) because it is bound to the edit-row input.

## Decision Rationale (contested assignments)

- **Submit→Approve / Submit→Reject (`TC-001`, `TC-002`) → E2E.** The transition is an API contract, but the
  feature's value is the *two-role browser journey with a session hand-off*. Acting in the browser and
  asserting the persisted state via API in the same test gives defense-in-depth without duplicating the
  whole journey at two layers.
- **`TC-203` (ESS can't approve) → API, not E2E.** There is no UI affordance to even attempt it as ESS (the
  supervisor view is blocked), so the only way to exercise the escalation guard is a direct `PUT`.
- **State guards (`TC-300`, `TC-301`) → API.** Backend rejections with no UI trigger (buttons aren't
  rendered) → direct `PUT`. Driving them through a browser would be an anti-pattern.
- **Uniqueness / report-feed (`TC-102`, `TC-103`) → API.** Pure data-contract checks, lowest adequate layer.
- **ESS hour validation (`TC-302`) kept at E2E.** Enforced in the edit-row cell; the user-facing inline
  error is what we protect (the API contract for it is already covered by the My Timesheet suite).

---

## Anti-Patterns Checked
- **No input-validation / error-codes at E2E creep**: backend state rejections (`300/301`) and escalation
  (`203`) live at API. ✅
- **Critical flows have E2E**: both Approve and Reject *cross-role* journeys are E2E. ✅
- **Not an ice-cream cone**: only the genuine two-role/journey scenarios are E2E; contract-shaped checks are
  pushed to API. ✅
- **Reuse, not duplication**: single-view mechanics already covered by `my-timesheets.spec.ts` and
  `employee-timesheets.spec.ts`; this suite tests only what those can't — the hand-off. ✅
