## Decision Rationale — contested calls

- **TC-403 (XSS) held at P1, not P0.** By the rulebook "security/compliance → P0." It's pulled down one notch because (a) Vue/OXD auto-escapes interpolated text so regression likelihood is low, and (b) the value's storage round-trip is independently asserted at the API layer. It remains P1 (not P2) because the *impact* if it ever regresses — stored XSS hitting reviewers/admins — is severe. Documented so a reviewer can promote it to P0 if the org treats any XSS surface as release-blocking.

- **TC-503 / TC-504 / TC-508 at P1, not P0.** Each protects the primary write path (validation gate, success signal, edit-permission UI), but each has a backstop: the backend rejects bad input (API TC-300–302), mutation scope is enforced server-side (API TC-105), and a missing toast doesn't lose data. P0 is reserved for the journeys whose failure alone makes the feature unusable (TC-001/002/004) — these *harden* those journeys rather than *being* them.

- **TC-005 / TC-006 at P1, not P2.** Tempting to treat them as duplicates of TC-004, but the three achievement categories carry different business semantics (positive recognition vs. development need vs. neutral note). Mis-saving a category corrupts the feedback record, so each primary category warrants a primary-path test. TC-004 alone earns P0 as the representative write journey; the other two ride at P1.

- **TC-101 (Admin menu) at P2, not P0.** Although RBAC-flavored, it's a *menu-visibility* check, not an access-control breach — server-side data groups (API TC-206) actually enforce the boundary. A visible-but-dead menu is a presentation defect, hence P2.

- **TC-505 (delete confirm) at P2, not P1.** It prevents accidental data loss, but a self-authored log is trivially recreatable, and the core delete action is already P1 (TC-008). The confirmation dialog is a guard rail, not the function itself.

- **Enterprise/AI E2E (TC-110, TC-509, TC-510) at P3.** These cannot pass on the actual Open Source target — they're skipped by the feature probe. Ranking them above P3 would misrepresent release risk for the OS build. Kept in the suite (P3) so they activate automatically if/when run against an Enterprise instance.
