# Test Strategy — Attendance → Employee Timesheets

> Feature: **Time → Timesheets → Employee Timesheets** (`/time/viewEmployeeTimesheet`).
> Input: `docs/test-scenarios_Attendance -> Employee timesheets.md` (37 scenarios).
> Generated by `/test-strategy`. Consumed by `/define-priority`.

This view is a **full-stack, role-gated, stateful workflow** (look up a subordinate → see their submitted
timesheet → Approve/Reject with side effects on state, the action log, and reports). The interesting risk
lives in the **multi-page journey + access control + state-machine transitions** — so the pyramid is wider
at the API layer (state transitions, contracts, authz) and keeps a focused band of E2E for the
approve/reject journeys a user actually performs. There is **no pure client-only logic** here (no
client-side validation beyond the mandatory reject comment), so there are **no Unit/Component** assignments.

## Decision Rationale (contested assignments)

- **Approve/Reject (`TC-003`, `TC-004`) → E2E (with API post-assert), not pure API.** The transition itself is
  an API contract, but the *value* of this feature is the supervisor performing it through the lookup→view→action
  journey, and the disappearing buttons + action-log row are UI consequences. We act in the browser and assert
  the persisted state via the employee-scoped API in the same test — defense-in-depth without duplicating the
  whole journey at two layers.
- **Access control split (`TC-200/203` E2E vs `TC-204/205` API).** Menu visibility and route redirect are the
  user-facing guard → E2E. The raw "ESS can't approve/read via API" is an authz contract that must hold even if
  the UI hides the button → API. Critical security rule, so tested at both layers deliberately.
- **State guards (`TC-301`, `TC-302`, `TC-305`) → API, not E2E.** These are backend state-machine rejections
  with no UI affordance to trigger them (the buttons aren't even rendered), so the only way to exercise them is
  a direct `PUT`. Pushing them to E2E would be an anti-pattern (API error codes tested through a browser).
- **Week-structure / uniqueness / report-feed (`TC-104`, `TC-106`, `TC-103`) → API.** Pure data-contract checks
  with no rendering nuance → lowest adequate layer.
- **Reject-comment-required (`TC-300`) kept at E2E.** It is enforced in the modal; the user-facing "Required"
  message is what we protect. The API equivalent is `TC-302`.

---

## Anti-Patterns Checked

- **No input-validation-at-E2E creep**: backend state rejections (`301/302/305`) live at API, not E2E. ✅
- **No API-error-codes-through-the-browser**: authz/contract failures asserted via direct `PUT`/`GET`. ✅
- **Critical flows have E2E**: Approve and Reject journeys both have E2E coverage. ✅
- **Not an ice-cream cone**: only the genuinely UI/journey scenarios are E2E; everything contract-shaped is
  pushed down to API. ✅
- **Existing suite (`tests/time/my-timesheets.spec.ts`)**: follows the same act-in-browser / assert-via-API
  pattern and seeds Customer→Project→Activity + fresh weeks via API — reused here, no anti-pattern observed.
