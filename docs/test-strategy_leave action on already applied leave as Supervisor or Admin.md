# Test Strategy: Leave Action on Already-Applied Leave (Supervisor or Admin)

> Input: `docs/test-scenarios_leave action on already applied leave as Supervisor or Admin.md` (33 scenarios)
> Knowledge: `orangehrm-opensource-domain` (business-rules §4, api-reference Leave),
> `playwright-best-practices`, existing `tests/leave/*.spec.ts`.
> Generated by `test-strategy` skill.

## Decision Lens

The feature is an inherently **stateful, role-gated, multi-page workflow**: a request must
already exist in a specific status, the actor's role governs visibility, and the action
mutates persisted state + leave balance. There is no pure logic to unit-test in this repo
(backend is out of scope) and no isolated Vue component under test here — so the realistic
layers are **E2E** (drive the Leave List UI) and **API** (assert backend authorization /
error contracts that are wasteful or impossible to prove through the UI).

Guiding rules applied:
- **Role authorization that returns an HTTP code** (ESS → 403, bad id → 404) → **API** — cheaper and unambiguous at the contract layer.
- **Balance/escrow math** → verified during E2E via the existing `LeaveEntitlementsApi` balance read (a hybrid E2E assertion), not a separate layer.
- **Anything a user actually sees/does** (Approve/Reject/Cancel from the grid, action visibility per status, toasts, status relabel) → **E2E**.

## Decision Rationale (Contested Assignments)

- **TC-100/101/102/103/401/403 (balance math)** — assigned **E2E** rather than a separate API
  test because the *trigger* is a UI action and the existing suites already verify balance via
  `LeaveEntitlementsApi.getEntitlementBalance` inside an E2E test (see `assign-leave.spec.ts`
  TC-104/108). Keeping the trigger and assertion together avoids re-implementing the action at the
  API layer and proves the real user path end-to-end.
- **TC-203 (ESS forbidden)** — **API**. The UI already hides the action from ESS (covered by TC-200),
  so the residual risk is a backend that fails to enforce it. That is a pure authorization-contract
  check → push DOWN to API (403). Testing it through the UI would be redundant with TC-200.
- **TC-302 (bad id 404)** — **API**. No UI path constructs an action against a non-existent id; this
  is an error-code contract only.
- **TC-104/105/300/500/501 (action visibility per status)** — **E2E**. These assert what the OXD
  Action control renders for a given status; that rendering is the thing under test, so it belongs
  at the UI layer (no lower layer exposes it).

## Anti-Patterns Checked (existing tests)

- Existing leave suites correctly keep input-validation (Required) checks in E2E only because they
  are OXD inline-render behaviors, and push authorization to role-gated UI checks. No ice-cream-cone
  violation found.
- This strategy avoids the common trap of asserting 403/404 through the browser by routing TC-203
  and TC-302 to the API layer.

## Defense-in-Depth Notes

- ESS-cannot-action is covered at **two layers**: UI route/menu gating (TC-200) and API authorization
  (TC-203) — intentional redundancy for a security-critical rule.
- Balance integrity is covered at the **action level** (TC-100–103) and the **boundary** (TC-403).
