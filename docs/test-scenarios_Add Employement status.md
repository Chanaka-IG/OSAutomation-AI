# Test Scenarios: Add Employment Status (`Admin → Job → Employment Status`)

> Feature: managing Employment Status records — list page `/admin/employmentStatus`, add form
> `/admin/saveEmploymentStatus`, and the edit page `/admin/saveEmploymentStatus/{id}`. A
> single-field (Name only) Admin-only configuration entity that feeds the PIM Job Details
> "Employment Status" dropdown (`empStatusId`).
> Source: `orangehrm-opensource-domain` (SKILL.md Employee.empStatusId, business-rules.md §9/§10/§11,
> api-reference.md Admin–Employment Status, ui-selectors.md Admin patterns) **plus live-app ground
> truth captured via Playwright MCP on the kord instance (2026-06-09)**.
> Generated by `create-scenarios` skill.

## Context & Verified Ground Truth (live app, Admin role)

### List page `/admin/employmentStatus`
- `<h6>` **"Employment Status"**, **Add** button, records counter **`(4) Records Found`**.
- Table columns: checkbox / **Employment Status** / **Actions** (note: the data column header is
  "Employment Status", NOT "Name").
- Row action icons: **trash FIRST, then pencil-fill** (delete before edit — same order as Job Titles
  and Pay Grades; verified live via icon classes `bi-trash` then `bi-pencil-fill`).
- List load: `GET /api/v2/admin/employment-statuses?limit=50&offset=0` → 200.
- **Seeded statuses (4, master data — do NOT mutate or delete)**: `Intern` (id 3), `Permanent`,
  `Probation`, `Terminated`.

### Add form `/admin/saveEmploymentStatus`
- `<h6>` **"Add Employment Status"**; a **single field**: **Name\*** (text, required).
- "* Required" legend, **Cancel** and **Save** buttons. **No `maxlength` attribute** on the input
  (length is enforced by reactive validation, not the browser).
- **Validation (observed live)**:
  - Empty Name + Save → inline **`Required`** under Name; no POST; stays on form.
  - Duplicate name → inline **`Already exists`** — fires **live while typing** (async check),
    tested against seeded `Permanent`.
  - Name > 50 chars → inline **`Should not exceed 50 characters`** **while typing**
    (live, not on save). ⚠ Employment-status limit is **50** (Job Titles is 100 — do not reuse that
    number; this matches Pay Grades).
- **Happy path (verified)**: Save with a unique name → **redirects to the LIST page
  `/admin/employmentStatus`** (it does **NOT** stay on an edit page, unlike Pay Grades). Counter
  increments by 1 and a green success toast (`.oxd-toast--success`, "Successfully Saved") fires.

### Edit page `/admin/saveEmploymentStatus/{id}`
- `<h6>` **"Edit Employment Status"**; the same single Name field, pre-filled, editable, with its
  own **Save** / **Cancel**. Same validation rules as Add. (Verified: opening Intern → URL
  `/admin/saveEmploymentStatus/3`, Name pre-filled `Intern`.)

### Delete (list page)
- Trash icon → confirmation dialog: title **"Are you Sure?"**, body **"The selected record will
  be permanently deleted. Are you sure you want to continue?"**, buttons **"No, Cancel"** /
  **"Yes, Delete"** (verified copy, identical to Job Titles / Pay Grades).
- `DELETE /api/v2/admin/employment-statuses` body `{ "ids": [n] }` → 200; list reloads and the
  counter decrements.
- Employment statuses are **hard-deleted** but deletion is **BLOCKED** when referenced by an
  Employee's job record: `"This record is in use and cannot be deleted"` (business-rules §11).
  The seeded statuses (Permanent etc.) are likely in use — do not attempt to delete them.

### API
- `GET /api/v2/admin/employment-statuses?limit=50&offset=0` — list (verified 200).
- `POST /api/v2/admin/employment-statuses` body `{ name }` — create (verified 200,
  api-reference Admin–Employment Status).
- `DELETE /api/v2/admin/employment-statuses` body `{ ids: [...] }` — bulk hard delete (verified 200).

### Security
- ESS users have **no Admin menu** (business-rules §2); admin endpoints return **403** for ESS
  sessions; unauthenticated requests redirect to login / 401 (business-rules §1).

## Happy Path (TC-001–099)

### TC-001: Admin adds an employment status with a unique Name
**Category**: Happy Path
**Preconditions**: Logged in as Admin; Name is unique (timestamped test data).
**Steps**:
1. Admin → Job → Employment Status → click **Add**.
2. Fill **Name** with a unique value.
3. Click **Save**.
**Expected Results**: Save succeeds; app **redirects to the list `/admin/employmentStatus`**; a green
success toast (`.oxd-toast--success`) fires; the new row appears and the counter increments by 1
(`(N)` → `(N+1) Records Found`).
**Business Rule**: Only `name` is mandatory (`POST /admin/employment-statuses { name }`).
**Suggested Layer**: E2E

### TC-002: New status appears in the list and increments the counter
**Category**: Happy Path
**Preconditions**: Admin; a status created this session.
**Steps**: After save, on `/admin/employmentStatus`, locate the new row.
**Expected Results**: Row present in the Employment Status column; counter incremented by 1.
**Business Rule**: List reflects created records.
**Suggested Layer**: E2E (asserted within TC-001 run)

### TC-003: Admin renames an existing (test-created) employment status
**Category**: Happy Path
**Preconditions**: A test-created status exists (never a seeded one).
**Steps**: Click its pencil → edit page `/admin/saveEmploymentStatus/{id}`; change **Name** to a new
unique value; Save.
**Expected Results**: Success toast; redirect to list; row shows the updated name; record count unchanged.
**Business Rule**: Name is editable post-create (`PUT`/save on edit page).
**Suggested Layer**: E2E

### TC-004: Cancel on the Add form abandons creation
**Category**: Happy Path
**Preconditions**: Admin on the Add Employment Status form with a filled Name.
**Steps**: Click **Cancel**.
**Expected Results**: Back on `/admin/employmentStatus`; record count unchanged; no new row; no POST.
**Business Rule**: Cancel is non-mutating.
**Suggested Layer**: E2E

### TC-005: New status is selectable in PIM Job Details
**Category**: Happy Path
**Preconditions**: A status created this session.
**Steps**: Open PIM → an employee → **Job** tab → open the **Employment Status** dropdown.
**Expected Results**: The new status is listed and selectable (feeds `empStatusId`).
**Business Rule**: PIM job records reference employment statuses by FK (`empStatusId`).
**Suggested Layer**: API (GET reflects the new id) + one E2E smoke

## Business Rules (TC-100–199)

### TC-101: Name is required
**Category**: Business Rule
**Preconditions**: Admin on the Add form.
**Steps**: Leave **Name** empty → Save.
**Expected Results**: Inline **`Required`** under Name (verified live); no POST; stays on form.
**Business Rule**: Required-field validation (business-rules §9).
**Suggested Layer**: Component / E2E (combined validation test)

### TC-102: Duplicate name is rejected with live inline "Already exists"
**Category**: Business Rule
**Preconditions**: Seeded status `Permanent` exists.
**Steps**: Type `Permanent` into Name; pause for the async check.
**Expected Results**: Inline **`Already exists`** appears **before Save** (verified live); saving must
not create a duplicate.
**Business Rule**: Unique employment-status name (business-rules §9 "Unique violations").
**Suggested Layer**: E2E

### TC-103: Name longer than 50 characters is blocked
**Category**: Business Rule
**Preconditions**: Admin on the Add form.
**Steps**: Type a 51+ char string into Name.
**Expected Results**: Inline **`Should not exceed 50 characters`** appears live (verified); Save does
not create the record.
**Business Rule**: Max name length = **50** (verified live).
**Suggested Layer**: Component / E2E (combined validation test)

### TC-104: Exactly 50 characters is accepted (boundary)
**Category**: Business Rule
**Preconditions**: Admin; unique 50-char name.
**Steps**: Enter a 50-char unique name → Save.
**Expected Results**: No length error; record created with the full 50-char string.
**Business Rule**: Boundary of the 50-char limit.
**Suggested Layer**: API (UI boundary smoke optional)

### TC-105: Employment status in use cannot be deleted
**Category**: Business Rule
**Preconditions**: An employment status referenced by an employee's job record (e.g. seeded
`Permanent`).
**Steps**: From the list, trash that status → confirm **Yes, Delete**.
**Expected Results**: Error toast **`This record is in use and cannot be deleted`**; row remains.
**Business Rule**: FK-protected hard delete (business-rules §11).
**Suggested Layer**: API (E2E optional — read-only assertion, must not actually remove seeded data)

**Expected Results**: UI redirects to `/auth/login`; API POST → 401/302.
**Business Rule**: Session-gated UI (business-rules §1).
**Suggested Layer**: API + one E2E assertion

**Expected Results**: Record NOT created — inline `Required` or backend 422.
(Assert "no new record" rather than a specific message.)
**Business Rule**: Required ⇒ non-blank.

### TC-302: API rejects > 50-char name (server-side parity)

**Expected Results**: 422 (duplicate); list still contains exactly one `Permanent`.

**Suggested Layer**: API
