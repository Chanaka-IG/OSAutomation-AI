  `openEditFormForName`, `deleteRowByName`); assertions stay in the test file.
- **No hardcoded data (§5)**: all routes, URL patterns, messages, dialog copy and samples come from

  collisions, no pollution of the seeded four.
- **Self-contained + serial (§11)**: `test.describe.configure({ mode: 'serial' })`, `workers:1`, each

  Probation/Terminated) was left intact.

- **Layer fit (domain)**: the spec carries only genuinely browser-shaped scenarios (live inline

- **Auto-waiting (§9)**: no `waitForTimeout`; relies on `expect(...).toBeVisible()` and loader-gone
  helpers. The XSS test correctly waits on `domcontentloaded` and asserts no dialog fired + no inline
  script node — a real non-execution proof, not a text check.
- **Comments (§12)**: `// -- Step N --` blocks only where multi-step flow needs narration; simple
  actions are left uncommented.

### Issues Found

#### [IMPORTANT] API seeding performed inside the test body, not a hook — TC-003 (lines ~168-171) and TC-505 (lines ~201-204)
```ts
// TC-003
await orangehrmAdminApi.loginAsAdmin();
const api = new EmploymentStatusesApi(orangehrmAdminApi.request);
await api.create({ name: original });
```
**Rule violated**: best-practices §5 "Add data via APIs" — *"Don't add data through APIs inside the
test body, always add data through APIs in the test hooks (beforeEach or beforeAll)."*
**Assessment**: real deviation, but **low risk here** — the suite is serial/`workers:1`, each test owns
a uniquely-timestamped record, and the same in-body seeding pattern is used by the reference
`add-job-title.spec.ts` (TC-505). Because the two P2 tests have *different* seed needs (rename needs
one record; delete needs a throwaway), a single shared `beforeEach` seed would be wasteful.
**Fix (optional)**: move each test's seed into a describe-scoped `beforeAll`/`beforeEach` that creates
the record and stashes the name, or leave as-is and accept the documented exception. Recommend
**leave as-is** for parity with the existing admin suites; not worth a structural change.

#### [SUGGESTION] `nameInput` / `recordsFoundText` use last-resort CSS selectors — `EmploymentStatusPage.ts` (lines 43, 56)
```ts
this.nameInput = page.locator('.oxd-form input.oxd-input');
this.recordsFoundText = page.locator('span').filter({ hasText: 'Records Found' });
```
**Rule referenced**: §2 locator priority (CSS = last resort) and "NEVER use index-based selectors
without filtering".
**Assessment**: **acceptable / unavoidable** — OXD inputs expose no role-name, label, placeholder, or
testid (confirmed live and in `ui-selectors.md`), so scoping the single form input via `.oxd-form` is
the most stable option and is exactly the pattern `JobTitlesPage`/`PayGradesPage` use. The `.oxd-form`
scope was deliberately added to avoid colliding with the sidebar "Search" `input.oxd-input` (a real
trap hit during MCP exploration) — good defensive choice, documented in the POM header comment.
**Fix**: none required. If the app team can add `data-testid` to the name field, prefer `getByTestId`.

#### [SUGGESTION] Row action icons selected by position — `EmploymentStatusPage.ts` (lines ~119, ~124)
```ts
await this.rowByName(name).locator('.oxd-icon-button').nth(1).click(); // edit (pencil)
await this.rowByName(name).locator('.oxd-icon-button').first().click(); // delete (trash)
```
**Rule referenced**: §2 "NEVER use index-based selectors".
**Assessment**: the index is **scoped to a single filtered row** and the icon order (trash then pencil)
was verified live via icon classes (`bi-trash`, `bi-pencil-fill`). This is the same scoped-index
pattern the reference `JobTitlesPage` uses for its trash icon, so it is consistent and low-risk.
**Fix (optional)**: harden to `locator('.oxd-icon-button:has(.bi-pencil-fill)')` /
`:has(.bi-trash)` to be order-independent. Nice-to-have, not required.

#### [SUGGESTION] TC-001 counter-delta assertion assumes no concurrent mutation
Line ~75: `expect(await employmentStatusPage.recordsFoundCount()).toBe(countBefore + 1)`.
**Assessment**: correct under `workers:1` + serial; would be flaky under parallel execution against a
shared instance. Documented here so a future parallelization effort revisits it. No change now.
