# Test Strategy — Attendance → Configuration

> Input: `docs/test-scenarios_Attendance -> Configuration.md` (28 scenarios).
> Generated by `/test-strategy`. Consumed by `/define-priority`.
>
> **Framework reality:** executable layers are **E2E** (`chromium`, `tests/**`) and **API**
> (`api`, `tests/api/**`) only — no component/unit harness. "Component"/"Unit" are conceptual.
>
> **Reuse:** prior Attendance pipelines built `AttendanceApi` (with `getConfigs`),
> `test-data/time/frontend/attendance.ts`, and the `PunchPage` (which exposes the disabled Date/Time
> fields for the downstream check). This feature adds an `AttendanceConfigPage` and `AttendanceApi.setConfigs`.

---

## 1. Distribution

| Layer | Count | Focus | Est. time |
|---|---|---|---|
| **E2E** | 18 | Toggle → Save → toast → persistence/reload, downstream effect on Punch In, admin-only access, UI rendering | ~4–6 min |
| **API** | 10 | `configs` GET/PUT contract: payload shape, per-flag persistence, singleton, authorization (ESS/anon forbidden), payload validation | ~1 min |
| **Component** | 0 (→ E2E) | OXD switch rendering — no mount harness | — |
| **Unit** | 0 | No client-side logic to unit-test | — |

> Defense-in-depth (per-flag persistence, full-payload PUT, authorization) is counted once at the primary
> layer with a secondary noted.

**Singleton caution (drives strategy):** this is one global config shared with every other Attendance suite,
which all assume **all flags OFF**. Every test that writes config MUST capture the prior values and **restore
them in `afterEach`/`afterAll`** (the `[[pim-optional-fields]]` singleton pattern). A leaked `true` would
break Punch-In/Out, My Records, and Employee Records suites.

## 3. Decision Rationale (contested assignments)

- **TC-002/004 (persist + reload) → E2E primary.** The value users trust is the rendered switch after a Save
  and a reload; the API GET is the secondary confirmation.
- **TC-006/103 → API primary.** Per-flag independence and the singleton property are contract facts —
  precise and fast at `configs` without UI noise.
- **TC-100/402 → E2E.** The whole point of the config is its **downstream effect**; enabling
  `canUserChangeCurrentTime` and observing the Punch In Date/Time fields flip enabled↔disabled is a genuine
  cross-feature E2E that reuses `PunchPage`.
- **TC-201/203/300/301 → API only.** Authorization (ESS/anon forbidden) and payload validation have no UI
  path beyond the "Credential Required" page (already TC-200) — they're contract tests.
- **TC-102 → API-leaning.** A supervisor role with subordinates is frequently unconfigured in the env; assert
  the flag/affordance at the contract, and only E2E it when supervisor creds exist (else skip with a note —
  no silent pass).

## 4. Anti-Patterns Found in Existing Tests
1. **Folded scenarios** in `tests/admin/add-work-shift.spec.ts` — forbidden by `generate-tests`. Configuration
   keeps **one test per scenario**.
2. **Singleton without restore** would be the dangerous anti-pattern here: a config write that isn't reverted
   poisons every other Attendance suite. Mitigation: capture-in-`beforeAll`, restore-in-`afterAll` (and revert
   per-test in `afterEach`), exactly as the PIM Optional Fields suite does (`[[pim-optional-fields]]`).
3. No existing coverage of the config screen or its downstream gating — closed here (TC-002/100/200).

## 5. Critical Flows Requiring E2E (non-negotiable)
- Toggle → Save → persist → reload: **TC-002, TC-004**.
- Downstream gating proof: **TC-100** (and its reversal **TC-402**).
- Admin-only access + unauthenticated redirect: **TC-200, TC-202**.
