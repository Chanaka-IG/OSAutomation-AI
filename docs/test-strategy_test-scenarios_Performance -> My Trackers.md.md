# Test Strategy — Performance → My Trackers

> **Input**: `docs/test-scenarios_Performance -> My Trackers.md` (63 scenarios)
> **Generated by**: `/test-strategy` — layer assignments for `/generate-tests`.
> **SUT**: OrangeHRM Open Source, driven via Playwright (`src/api/orangehrmOSAPI/*` for API, POM under `src/pages/*` for E2E).

## Available layers in THIS repo (hard constraint)

This automation repo has **two execution layers only**:

| Layer | Where | Mechanism |
|-------|-------|-----------|
| **API** | `tests/api/*.spec.ts` (+ API setup inside E2E suites) | `request.get/post/...` via `orangehrmAdminApi` / per-user `AuthApi` sessions; assert status codes + JSON payloads |
| **E2E** | `tests/<module>/*.spec.ts` | Browser + Page Objects (`src/pages/*`), OXD selectors, toasts |

There is **no Component layer** (no `@playwright/experimental-ct`) and **no Unit layer** — the system under test is a remote PHP/Symfony app, so there is nothing to unit-test from this TypeScript repo.

**Consequence for the decision rules:** "Pure function → Unit" and "single component → Component" have no home here. The PHP validators (`getNonEmptyStringValidator(150/3000)`, `v::in($allScaleIds)`, `v::arrayVal()->length(0,5)`) and the data-group/`self` permission logic ARE unit/integration-tested in the OrangeHRM backend repo (`orangehrmPerformanceTrackerPlugin/test/api/PerformanceTrackerLogsEndPointTest.php`, `...EndpointTestCases.yml`, `userrole/*Test.php`) — **out of scope** for this suite. Here, the **lowest adequate layer for any backend rule is API**, and we push every contract/validation/permission check down to it. E2E is reserved for genuine multi-page journeys, rendering, menu/session behavior, and OXD UI state.

## Decision Rationale (contested assignments)

**Validation TC-300 / TC-301 / TC-302 — split, don't duplicate.** The scenario doc suggested "E2E + API" for all three. Per the anti-pattern *"input validation tested at E2E should be API"*, the **contract assertion (422 + field error) lives at API** (one test each). The **inline `"Required"` UI rendering** is exercised **once** by the consolidated **TC-503**, rather than spinning up three browser tests that re-prove the same OXD behavior. This keeps the validation matrix at API where it's fast and exhaustive.

**Boundary lengths TC-400 / TC-401 → API only.** Char-boundary acceptance/rejection is a backend validator contract (`getNonEmptyStringValidator(N)`). Driving 150/151/3000/3001-char strings through a browser is slow and proves nothing extra. TC-506 (E2E) only checks that the UI *gives feedback*, not the exact backend cutoff.

**Self-scope & permissions (TC-100, TC-102, TC-105, TC-200–204, TC-206, TC-407) → API primary.** These are pure data-group/`self` authorization outcomes (HTTP 403 / filtered lists) — the canonical API layer. The cross-user 403 cases (TC-200–204) are **API-only** because there is no UI path for a user to even attempt another employee's tracker; the meaningful test is a direct request with a foreign `trackerId`/`id` under the victim-other session. The few that also carry a **visible UI consequence** (TC-100 list contents, TC-102 missing Add button, TC-105 missing edit/delete controls, TC-206 missing menu, TC-407 absent tracker) get a **secondary E2E** for defense-in-depth on the user-facing surface.

**Log CRUD (TC-004/007/008) → E2E primary + API secondary.** The user value is the Add/Edit/Delete *journey* (form, toast, dialog), so E2E owns it. But the persistence contract (correct `achievement`, `userId` attribution, actual deletion) is cheaply and deterministically asserted at **API** — so each gets a thin API companion. This is intentional defense-in-depth on the most important happy paths.

**Feedback summary TC-003 → API.** It's a numeric aggregation contract (`TrackerFeedbackSummaryEndpoint`); asserting counts via JSON is exact, whereas reading them off a widget is brittle. The widget *render* is implicitly covered when TC-002/TC-502 open a tracker.

**XSS TC-403 → E2E primary.** Output-encoding can only be verified where the markup is actually rendered (no `<script>` execution, escaped entities). API secondary confirms the raw value round-trips unmodified in storage, isolating "stored as-is, escaped on render."

**Session redirect TC-205 & menu visibility TC-101 → E2E.** Both are browser/session/role-render behaviors with no API equivalent worth asserting.

**Enterprise-conditional set → keep at the assigned layer but gate.** `visibleToEmployee` hiding, attachments, AI heading, CSV export are present in the source tree but gated to Enterprise/AI. They stay mapped to API/E2E as appropriate, wrapped in a runtime feature-detect (`test.skip` if the control/endpoint is absent) so a stock Open Source run doesn't red-fail. Generate-tests should probe once in `beforeAll` and skip the group.

## Data & Setup Strategy (for /generate-tests)

The hard part of this feature is **fixtures**: a tracker must exist with the **logged-in ESS user as its subject**, plus a **reviewer** and **cross-user** actors. ESS cannot create trackers, so seeding is an **Admin/reviewer** action.

- **Seed in `beforeAll` via Admin API**: create employees A (subject), B (other subject), R (reviewer); create ESS users for A and B (pattern: `EmployeesApi.createIfAbsent` + `AdminUsersApi.createIfAbsent`, as in `addKpis.spec.ts`).
- Create a tracker for A (subject=A, reviewer=R) and a tracker for B — via `POST /api/performance-trackers` under an Admin session. **No `*Api` client exists yet** for trackers under `src/api/orangehrmOSAPI/` → `/generate-tests` should add `PerformanceTrackersApi.ts` + `PerformanceTrackerLogsApi.ts` (mirror `LeaveRequestsApi.ts`).
- **Per-user sessions** for self-scope/security tests: log in as A and B with `AuthApi` (see `leave-action.spec.ts` for the multi-user session pattern) and issue requests with each session.
- **Page Object**: add `src/pages/performance/MyTrackersPage.ts` (list, open tracker, Add Log modal, achievement dropdown, toast, delete dialog).
- **Cleanup in `afterAll`**: delete seeded employees/trackers. Do **not** leave it commented out (see anti-patterns).
- **Enterprise probe**: in `beforeAll`, GET a capability marker (e.g. attachments field / AI endpoint) and set a `featureFlags` object the conditional tests read.

## Anti-Patterns Found in Existing Tests

Reviewed `tests/performance/addKpis.spec.ts` and the API template `tests/api/pim-employees.spec.ts`.

1. **`test.only` left in committed code** — `addKpis.spec.ts` line ~`test.only('TC-010 …')`. This **silently disables every other test in the file** (TC-001, TC-005 never run in CI). 🚩 High severity. `/generate-tests` must never emit `test.only`; add an ESLint guard (`no-only-tests`) if available.
2. **Cleanup commented out** — the `afterAll` that deletes seeded KPIs is fully commented. Leaves data in the SUT, causing order-dependence and "Already exists" flakiness on reruns. My Trackers suite **must** implement real teardown.
3. **Title-string coupling for setup branching** — `if (testInfo.title.includes('TC-203')) return;` in `beforeEach`. Brittle: renaming a test breaks setup. Prefer fixtures/tags or per-test `beforeEach` scoping.
4. **Validation only at E2E for KPIs** — there are no API-layer tests asserting KPI field validation/422s; it's all driven through the browser. Don't repeat this for trackers — the **TC-300s/400s belong at API** (this strategy enforces that).
5. **Good pattern to copy** — `tests/api/pim-employees.spec.ts` is the right API template: explicit `401/403` no-session check, JSON payload contract assertions, dedicated seed via `ensureEmployeeRecords`. Model `PerformanceTracker` API tests on it.
