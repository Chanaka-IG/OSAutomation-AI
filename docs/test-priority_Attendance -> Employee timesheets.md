# Test Priority — Attendance → Employee Timesheets

> Feature: **Time → Timesheets → Employee Timesheets** (`/time/viewEmployeeTimesheet`).
> Input: `docs/test-strategy_Attendance -> Employee timesheets.md` (E2E-layer scenarios only).
> Generated by `/define-priority`. Consumed by `/generate-tests`.

Scope: only the **E2E** scenarios are prioritized below (API/Component/Unit are excluded per the skill).
Priority reflects business impact, failure risk, and user reach for the supervisor approval workflow.

---

## P0 — Release-blocking (core flow, security, data integrity, no workaround)

| ID | Scenario | Rationale |
|---|---|---|
| TC-002 | Select an employee and view their timesheet | The entry point of the whole feature; if lookup→view is broken, nothing else works. No workaround. |
| TC-003 | Approve a submitted timesheet | The primary purpose of the screen; approval gates whether hours count toward reports — data integrity. |
| TC-004 | Reject a submitted timesheet with a comment | The other half of the core workflow; returns the timesheet to the employee. No workaround in this view. |
| TC-200 | Non-supervisor ESS cannot access Employee Timesheets | Access-control boundary; a leak exposes/edits others' data — security/compliance. |
| TC-203 | Unauthenticated access redirects to login | Auth guard on a privileged route; release-blocking security baseline. |

## P1 — High impact (primary path, high reach, major integration)

| ID | Scenario | Rationale |
|---|---|---|
| TC-001 | Employee Timesheets opens with an employee selector | First-load of the primary screen; high reach, precedes every action. |
| TC-100 | Approve/Reject offered only for a SUBMITTED timesheet | Guards the state machine at the UI; prevents invalid actions on the common path. |
| TC-201 | Admin can view any employee's timesheet | Core admin capability; high reach for HR admins. |
| TC-300 | Reject without a comment is blocked | Enforces the mandatory-comment business rule on the primary reject path. |
| TC-500 | Buttons reflect state (Submitted → Approve+Reject) | Directly drives whether the user can act; high-impact rendering correctness. |
| TC-501 | Reject opens a comment modal with a mandatory field | The reject path depends on this modal; primary-feature UI. |
| TC-006 | Action log shows the approval performer and date | Auditability of approvals — a key integration/compliance expectation. |

## Notes for `/generate-tests`
- **P0 + P1 = 12 scenarios.** Per the generate-tests rule ("write P0+P1 only if ≥12 together"), the suite
  targets **P0 + P1 (12 E2E tests)**. P2/P3 are out of scope for generation unless the count drops below 12.
- Several P0/P1 tests assert their **post-condition via the employee-scoped API** (the established
  `my-timesheets.spec.ts` pattern), so Step 4 must wrap `/time/employees/{empNumber}/timesheets/…`.
- `TC-202` (supervisor-only scoping) is **env-gated** on a configured supervisor account; if unavailable it is
  P2 and may be skipped — it is *not* in the P0/P1 generation set, so it does not block the suite.
