# Test Strategy — Attendance → Employee Records

> Input: `docs/test-scenarios_Attendance -> Employee records.md` (36 scenarios).
> Generated by `/test-strategy`. Consumed by `/define-priority`.
>
> **Framework reality:** executable layers are **E2E** (`chromium`, `tests/**`) and **API**
> (`api`, `tests/api/**`) only — no component/unit harness. "Component"/"Unit" are conceptual; everything
> that runs maps to **E2E** or **API**.
>
> **Reuse:** prior Attendance pipelines built `AttendanceApi`, `MyAttendanceRecordsPage`, and
> `test-data/time/frontend/attendance.ts`. This feature adds an `EmployeeAttendanceRecordsPage` (summary +
> detail) and a `getEmployeeSummary(date)` API reader; the detail grid reuses the My-Records row patterns.

---

## 1. Distribution

| Layer | Count | Focus | Est. time |
|---|---|---|---|
| **E2E** | 25 | Summary list, date/employee filter → query, row/filter "View" → detail navigation, detail grid, empty state, panel toggle, admin-only access, no-edit affordance, auth redirect | ~6–9 min |
| **API** | 11 | `employees/summary` & `employees/{n}/records` contracts: per-employee sum, employee count, detail scope, authorization (ESS forbidden), pagination, timezone, termination | ~1–2 min |
| **Component** | 0 (→ E2E) | OXD summary/detail row + empty-state rendering — no mount harness | — |
| **Unit** | 0 | Sums computed server-side → API | — |

> Defense-in-depth cases (per-employee total, employee count, detail scope, admin authorization, timezone)
> are counted once at their primary layer and noted with a secondary layer.

This feature is **navigation-heavy**: summary → (row/filter View) → detail is a genuine multi-page journey
that only E2E exercises, while the two list/aggregation contracts and authorization are cheapest at API.

## 3. Decision Rationale (contested assignments)

- **TC-004/005 (View → detail) → E2E.** The whole point is the navigation contract (row/filter View builds
  `?employeeId&date` and loads the detail grid) — only the browser exercises it end-to-end.
- **TC-102/103/104 → API primary.** Per-employee sums, detail scoping, and "admin sees all" are
  aggregation/authorization rules that are precise and fast at the contract; the E2E legs (TC-001/006) cover
  the rendered side incidentally.
- **TC-204 → API only.** ESS-forbidden on `employees/summary` / `employees/{n}/records` has no UI path
  beyond the "Credential Required" page (already TC-200/201); the raw 403 is a contract test.
- **TC-400/401 (pagination) → API.** Creating >50 employees/records through the UI is impractical; `limit`/
  `offset` is a contract concern. Flag the cap rather than silently truncate.
- **Seeding constraint (carried from prior Attendance pipelines):** punches can only be created at *current*
  server time (`canUserChangeCurrentTime=false` → past/future punch returns `400`). So detail-bearing tests
  seed **today** for the **admin's own employee (Ruwan, empNumber 1)** via `AttendanceApi` and assert on
  **unique notes**; empty-detail uses a **far-past date** (always empty, viewable). Summary tests key off the
  **stable seeded master-data employees** (Ruwan Kumara, Marcus Chen, …) rather than fabricated rows.

## 4. Anti-Patterns Found in Existing Tests
1. **Folded scenarios** in `tests/admin/add-work-shift.spec.ts` — forbidden by `generate-tests`. Employee
   Records keeps **one test per scenario**.
2. **Un-cleanable records** → absolute counts flake. Reuse the established mitigation: unique notes +
   API-derived counts bounded by the 50-row page size (see `[[`review-fixes_Attendance -> My Records`]]`).
3. **No existing coverage** of the summary↔detail navigation or admin-only attendance authorization — closed
   here (TC-001/004/006/200/202).

## 5. Critical Flows Requiring E2E (non-negotiable)
- Summary loads, and View → detail navigation: **TC-001, TC-004, TC-006**.
- Admin-only access + unauthenticated redirect (authorization): **TC-200, TC-203**.
- No-modify affordance under default config + required-date validation: **TC-202, TC-300**.
