## `tests/time/timesheet-lifecycle.spec.ts`

### What's Good
- **Genuine cross-role journeys with a real session hand-off**: one test logs in as ESS, submits in the
  browser, then `loginAs('admin')` (which clears cookies) and actions it — exactly the integration the
  feature exists for, and the only layer that can prove it. Strong altitude choice.
- **Defense-in-depth**: every journey asserts the rendered badge *and* the persisted state via
  `EmployeeTimesheetsApi.getEntries(...).meta.timesheet.status.id` — UI + contract in one test.
- **Isolation**: each test consumes a distinct fresh past week (`claimFreshWeek`), so timesheets
  (one-per-week, undeletable) never collide; re-runs are idempotent (create-if-absent seed).
- **No anti-patterns**: no `waitForTimeout`, no `test.only`, no hardcoded IDs/dates (all derived), locators
  only in the reused POMs, assertions in the spec.
- **Discrepancy surfaced**: TC-TSL-400 documents that OS 5.8 accepts an empty reject comment (domain skill
  says mandatory) instead of asserting a false rule.
- **Avoids redundancy honestly**: the header explicitly records that TC-302/501/502 are *not* re-implemented
  because the dedicated single-view suites already cover them — aligns with the anti-pattern guidance
  "don't write redundant tests" and the strategy's reuse note, rather than padding the count.
- **Root-caused, not patched-over**: the initial TC-TSL-004 failure was correctly traced to seeding the
  submit *admin-on-behalf* (so the log credited the admin, not the ESS); fixed by having the ESS submit
  through the UI — the right diagnosis, not a weakened assertion.

### Issues Found

**[SUGGESTION] No `afterAll`; teardown relies on stable reused identities.**
- The ESS employee/user and Customer/Project are stable **create-if-absent** identities, intentionally
  retained (employee deletes are environment-restricted on this shared instance, and a timesheeted project
  can't be hard-deleted anyway). This is documented in a header comment and is *not* a flake risk (fresh
  weeks per test). It does diverge from `leave-e2e-lifecycle.spec.ts`, which deletes its employees in
  `afterAll`. Acceptable as-is; the rationale comment should stay. No action required for correctness.

**[SUGGESTION] `essLogAndSubmit` uses inline `import('…').Type` annotations (lines ~118–121).**
- Functional and type-safe, but a top-of-file `import type { LoginPage } from …` / `{ MyTimesheetPage }`
  reads cleaner and matches the rest of the codebase's import style.

**[SUGGESTION] TC-TSL-401 is titled "Multi-day" but the scenario said "multi-row/day".**
- Implemented as a single row across two days (08:00 + 04:00 → 12:00), which validates row/day/grand totals
  without needing an `+ Add` row POM method. Faithful to the totals intent; the title already says
  "Multi-day", so just confirm the scenario doc cross-reference is clear. No code change needed.

**[SUGGESTION] `claimFreshWeek` mutates module-level `weekCursorDate`; tests are order-coupled on the cursor.**
- This mirrors the approved sibling `my-timesheets.spec.ts` pattern and is safe under the suite's serial
  (single-worker) execution, but worth a one-line note that the cursor is deliberately shared to hand out
  non-overlapping weeks.
