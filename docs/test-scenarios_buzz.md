# Test Scenarios: Buzz (`/buzz/viewBuzz`)

> Feature: the Buzz social newsfeed — employees create text/photo/video posts, like,
> comment, and reshare. Available to **Admin**, **ESS**, and **Supervisor** roles (Buzz is
> in the default menu of every role per `business-rules.md` §2).
> Sources: `orangehrm-opensource-domain` skill (menu visibility §2, global validation §9,
> toasts/loaders §10) **plus discovered code behavior from the OrangeHRM code repo**
> (`symfony/plugins/orangehrmBuzzPlugin` — `BuzzPostsEndpoint.php`,
> `VideoLinkValidatorEndpoint.php`, `CommentEndpoint.php`, `CommentsEndpoint.php`,
> `LikesEndpoint.php`, `BuzzConfigService.php`, `BuzzService.php`).
> Generated by `create-scenarios` skill.

## Context & Discovered Ground Truth (code-verified)

- **Post ("share") types**: `status` (text), `photo`, `video`, `reshare`
  (plus `kudos`, enterprise-only — see note at bottom).
  Source: `BuzzPostsEndpoint::getValidationRuleForPost` — `type` must be in
  `['status','video','kudos','photo','reshare']`.
- **Status post**: `text` is **mandatory and non-empty** for `type=status`;
  max length **65535** chars (`v::stringType()->length(0, 65535)->notEmpty()`).
- **Photo post**: `photos` array is mandatory, **1–5 photos** (`v::arrayVal()->length(1,5)`).
  Each photo needs `name` (non-empty), `size` ≤ configured max
  (`buzz_max_image_upload_size_mb` × 1,000,000 bytes), `type` in the configured valid
  photo types, and `base64` that decodes to a **real image**
  (`imagecreatefromstring` check — corrupt payloads rejected). Uploaded images are
  resized to a max dimension (default **1024px**, `buzz_image_max_dimension`).
- **Video post**: `video_link` mandatory and must pass the allow-list check
  (`ShareEndpointHelper::isUrlValid`): allowed domains are
  `www.youtube.com` / `youtu.be` / `youtube-nocookie.com`, `vimeo.com`,
  `www.dailymotion.com`, `www.yahoo.com`, `www.metacafe.com`, `www.ustream.tv`.
  A pre-validation endpoint (`validateVideoLink`) returns `{valid, url}` with the
  embed URL — the UI uses this to render the preview before posting.
- **Reshare**: `post_id` mandatory (must be a positive int referencing an existing post);
  optional `reshare_text` (non-empty if provided, ≤65535).
- **Comments**: `commentText` mandatory, non-empty, ≤65535 chars (add and edit).
- **Likes**: one like per user per share and per comment. A second like attempt returns
  `"User has already liked this share"` / `"User has already liked this comment"`.
- **Delete rules** (`BuzzPostsEndpoint::doDelete`): a user may delete **their own**
  shares; users with the `buzz_link` data-group **delete** permission (Admin) may delete
  anyone's. Requested ids are silently intersected with the allowed set — ids you may
  not delete are dropped, not errored. Deleting an **original post deletes the post AND
  its reshares**; deleting a **reshare** removes only the reshare.
- **Feed**: supports pagination (`limit` + `pageNo`) and ordering by
  `no of likes` / `no of comments` / `share time` — this backs the UI tabs
  **Most Recent Posts / Most Liked Posts / Most Commented Posts**.
- **Permissions**: every Buzz operation is gated on the `buzz_link` data group —
  read for GET, create for POST, delete for DELETE. All roles have Buzz by default.
- **Success/failure envelope**: create returns 201 + `"Successfully Saved"`;
  failures return 400 `"Failed to Save"` / `"Failed to Delete"`; missing kudos
  receiver / employees return 404; unauthenticated → 401; unauthorized → 403.
- Global UI conventions apply (domain skill §9–10): success/error **toast** bottom-right,
  skeleton loader while the feed fetches, `"Required"` inline validation.

> ⚠️ Selector/wording caveat: exact button labels ("What's on your mind?",
> "Share Video", "Share Photos", tab captions) should be confirmed against the live
> instance during implementation; the behaviors below are code-traced.

## Happy Path (TC-001–099)

### TC-001: Admin opens Buzz from the main menu
**Category**: Happy Path
**Preconditions**: Valid Admin credentials.
**Steps**:
1. Login as Admin.
2. Click **Buzz** in the left main menu.
**Expected Results**: URL is `/buzz/viewBuzz`; breadcrumb/header shows "Buzz"; the post
composer and the newsfeed (or its empty state) render; feed tab defaults to
**Most Recent Posts**.
**Business Rule**: §2 — Buzz is in the Admin menu; feed GET requires `buzz_link` read.
**Suggested Layer**: E2E

### TC-002: ESS user opens Buzz
**Category**: Happy Path
**Preconditions**: Enabled ESS user exists.
**Steps**:
1. Login as ESS.
2. Click **Buzz** in the menu.
**Expected Results**: Buzz page renders identically (composer + feed) — Buzz is not
Admin-only; ESS can see posts authored by all employees.
**Business Rule**: §2 — ESS default menu includes Buzz.
**Suggested Layer**: E2E

### TC-003: Create a text (status) post
**Category**: Happy Path
**Preconditions**: Logged in (any role); Buzz page open.
**Steps**:
1. Type a unique text (e.g. `Buzz smoke <timestamp>`) into the composer.
2. Click **Post**.
**Expected Results**: Success toast `"Successfully Saved"`; the post appears at the top
of **Most Recent Posts** with the author's name, avatar, and posted time; text matches
exactly.
**Business Rule**: `type=status` with non-empty `text` → 201 Saved.
**Suggested Layer**: E2E

### TC-004: Create a photo post with one image and caption
**Category**: Happy Path
**Preconditions**: Logged in; a valid `.jpg`/`.png` under the size limit available.
**Steps**:
1. Click **Share Photos** on the composer.
2. Add caption text, attach 1 valid image, click **Share/Post**.
**Expected Results**: Toast `"Successfully Saved"`; the post renders at the top of the
feed with the caption and the image displayed.
**Business Rule**: `type=photo` requires 1–5 photos of valid type/size.
**Suggested Layer**: E2E

### TC-005: Create a video post with a valid YouTube URL
**Category**: Happy Path
**Preconditions**: Logged in; a public YouTube video URL (`https://www.youtube.com/watch?v=…`).
**Steps**:
1. Click **Share Video**.
2. Paste the URL — wait for the embedded preview to render.
3. Add caption text and click **Share/Post**.
**Expected Results**: Preview appears after URL validation (validate-link call returns
`valid: true` + embed URL); after posting, the feed card contains the playable embedded
video iframe and the caption.
**Business Rule**: `video_link` must match the allowed-domain list; UI pre-validates via
`validateVideoLink`.
**Suggested Layer**: E2E

### TC-006: Create video posts with other supported providers (youtu.be, Vimeo)
**Category**: Happy Path
**Preconditions**: Logged in.
**Steps**:
1. Share a video using a `https://youtu.be/<id>` short link → post.
2. Share a second video using a `https://vimeo.com/<id>` link → post.
**Expected Results**: Both URLs validate (converted to their embed form, e.g.
`youtube.com/embed/<id>`, `player.vimeo.com/video/<id>`) and both posts render with
working embeds.
**Business Rule**: Allow-list includes `youtu.be`, `vimeo.com`, `www.dailymotion.com`, etc.
**Suggested Layer**: API (validate-link) + one E2E spot-check

### TC-007: Like a post and see the count increment
**Category**: Happy Path
**Preconditions**: At least one post exists (create via TC-003 setup).
**Steps**:
1. Note the post's current like count.
2. Click the **Like** (heart) control on the post.
**Expected Results**: The icon switches to the liked state immediately; like count
increments by 1; reloading the page preserves the liked state and count.
**Business Rule**: LikesEndpoint — like on share; one per user.
**Suggested Layer**: E2E

### TC-008: Unlike a previously liked post

**Expected Results**: Icon returns to unliked state; count decrements by 1; state

### TC-009: Comment on a post

### TC-010: Like a comment

**Preconditions**: A post with a comment exists (TC-009).
**Steps**: Click the like control on the comment.
**Expected Results**: Comment like registers (icon state + count = 1); persists on reload.

**Suggested Layer**: E2E

### TC-011: Edit own comment

### TC-013: Reshare another user's post with own text
**Category**: Happy Path

**Steps**:
1. As user B, click **Share** on A's post.
2. Enter reshare text in the modal and confirm.
**Expected Results**: A new feed card appears authored by B, containing B's reshare
text plus the embedded original post (A's name + original text); the original post's

**Suggested Layer**: E2E

### TC-014: Edit own post text
**Category**: Happy Path
**Preconditions**: Logged-in user authored a text post.
**Steps**:
1. Open the post's ⋮ (three-dots) menu → **Edit Post**.
2. Change the text and save.
**Expected Results**: Toast success; the card shows the updated text; other users see
the updated text (verify with a second session or reload).
**Business Rule**: Author can update own share; updated time changes.
**Suggested Layer**: E2E

### TC-015: Delete own post
**Category**: Happy Path
**Preconditions**: Logged-in user authored a post.
**Steps**:
1. Open ⋮ → **Delete Post**.
2. Confirm in the confirmation dialog.
**Expected Results**: Toast `"Successfully Deleted"` (or equivalent); the post is
removed from the feed and does not reappear on reload.

**Suggested Layer**: E2E

### TC-016: Feed tabs order posts correctly
**Category**: Happy Path
**Preconditions**: Seed 3 posts: P1 newest (0 likes/comments), P2 with 2 likes,
P3 with 2 comments.
**Steps**:
1. Open **Most Recent Posts** tab.
2. Switch to **Most Liked Posts**.
3. Switch to **Most Commented Posts**.

### TC-017: Feed pagination / infinite scroll loads older posts
**Category**: Happy Path
**Preconditions**: More posts exist than one feed page (seed >10 via API).
**Steps**:
1. Open Buzz; note the initially rendered post count.

**Category**: Happy Path
**Preconditions**: Authenticated session/token; posts exist.

## Business Rules (TC-100–199)

### TC-100: Text post requires non-empty text
**Category**: Business Rule
**Preconditions**: Buzz page open.
**Steps**:
1. Leave the composer empty and attempt to post (button click or API `type=status`
   with `text: ""`).
**Expected Results**: UI: the Post button is disabled or inline validation blocks
submission; no post is created. API: 400 — `text` fails `notEmpty`.
**Business Rule**: `type=status` → `text` mandatory + non-empty.
**Suggested Layer**: Component (button state) + API

### TC-101: Photo post requires at least one photo
**Category**: Business Rule
**Preconditions**: Share Photos modal open / API access.
**Steps**: Submit `type=photo` with an empty `photos` array (UI: try to share with no
file selected).
**Expected Results**: UI: share button disabled or validation error; API: 400
(`photos` length must be 1–5).
**Business Rule**: `v::arrayVal()->length(1,5)`.
**Suggested Layer**: API + Component

### TC-102: Photo post rejects more than 5 photos
**Category**: Business Rule
**Preconditions**: 6 valid small images prepared.
**Steps**: Attempt `type=photo` with 6 photos (UI: attach 6 files if the picker allows;
otherwise API).
**Expected Results**: Rejected — API 400; UI blocks the 6th attachment or shows an
error; no post created.
**Business Rule**: Max 5 photos per photo post.
**Suggested Layer**: API

### TC-103: Photo over the configured max upload size is rejected
**Category**: Business Rule
**Preconditions**: Know the instance's `buzz_max_image_upload_size_mb`; prepare an image
just over it.
**Steps**: Attach/submit the oversized image as a photo post.
**Expected Results**: Rejected with a size validation error; no post created.
**Business Rule**: photo `size` ≤ `buzz_max_image_upload_size_mb` × 1,000,000.
**Suggested Layer**: API

### TC-104: Non-image file type is rejected in photo post
**Category**: Business Rule
**Preconditions**: A `.txt`/`.pdf` file (and an image renamed to `.jpg` for TC-303).
**Steps**: Attempt to attach a non-image file type in the photo modal / API with
`type: "text/plain"`.
**Expected Results**: Rejected — photo `type` must be in the configured valid photo
types; no post created.
**Business Rule**: `v::key('type', v::in(validPhotoTypes))`.
**Suggested Layer**: API + one E2E check of the picker filter

### TC-105: Video post rejects URLs from unsupported domains
**Category**: Business Rule
**Preconditions**: Share Video modal open.
**Steps**: Paste `https://www.facebook.com/watch?v=123` (valid URL shape, unsupported
domain).
**Expected Results**: Validation fails — UI shows an invalid-URL message and disables
sharing; `validateVideoLink` returns `valid: false`; no post created.
**Business Rule**: Allow-list of video domains (YouTube/Vimeo/Dailymotion/Yahoo/
Metacafe/Ustream only).
**Suggested Layer**: API + E2E

### TC-106: One like per user per post
**Category**: Business Rule
**Preconditions**: User has already liked a post.
**Steps**: Re-submit the like for the same share via API (bypassing the UI toggle).
**Expected Results**: Rejected with error `"User has already liked this share"`; like
count remains unchanged.
**Business Rule**: LikesEndpoint duplicate-like guard.
**Suggested Layer**: API

### TC-107: One like per user per comment
**Category**: Business Rule
**Preconditions**: User has already liked a comment.
**Steps**: Re-submit the comment like via API.
**Expected Results**: Rejected with `"User has already liked this comment"`; count
unchanged.
**Business Rule**: LikesEndpoint duplicate-like guard (comments).
**Suggested Layer**: API

### TC-108: Comment cannot be empty (add and edit)
**Category**: Business Rule
**Preconditions**: A post exists; user has one existing comment.
**Steps**:
1. Try submitting an empty comment.
2. Try editing the existing comment to empty text.
**Expected Results**: Both blocked — UI: submit disabled/validation; API: 400
(`commentText` notEmpty).
**Business Rule**: `commentText` mandatory non-empty on create and update.
**Suggested Layer**: API + Component

### TC-109: Only the author sees Edit on a post
**Category**: Business Rule
**Preconditions**: Post by user A exists; user B logged in (non-admin ESS).
**Steps**: As B, open A's post card and inspect the ⋮ menu.
**Expected Results**: No **Edit Post** option for another user's post (B can only
like/comment/share it).
**Business Rule**: Shares are updatable by their author only.
**Suggested Layer**: E2E

### TC-110: Admin can delete another employee's post
**Category**: Business Rule
**Preconditions**: ESS-authored post exists; Admin logged in.
**Steps**: As Admin, ⋮ → Delete on the ESS post → confirm.
**Expected Results**: Post deleted from the feed for all users.
**Business Rule**: `buzz_link` data-group delete permission grants delete over
accessible shares (Admin).
**Suggested Layer**: E2E

### TC-111: Deleting an original post also removes its reshares
**Category**: Business Rule
**Preconditions**: Post P by user A; reshare R of P by user B.
**Steps**:
1. Delete P (as A or Admin).
2. Reload the feed.
**Expected Results**: Both P and R are gone from the feed.
**Business Rule**: `doDelete` — original share → `deletePosts` cascades; reshare rows
of that post are removed with it.
**Suggested Layer**: E2E (seed via API)

### TC-112: Deleting a reshare keeps the original post
**Category**: Business Rule
**Preconditions**: Post P by A; reshare R by B.
**Steps**: As B, delete R.
**Expected Results**: R disappears; P remains intact; P's share count decrements.
**Business Rule**: Reshare ids are deleted via `deleteReshares` only.
**Suggested Layer**: E2E

### TC-113: Reshare requires an existing post
**Category**: Business Rule
**Preconditions**: API access; a post id that has been deleted.
**Steps**: POST `type=reshare` with the deleted/nonexistent `post_id`.
**Expected Results**: 400 `"Failed to Save"` (or 404); no reshare appears in the feed.
**Business Rule**: `post_id` must reference a real post.
**Suggested Layer**: API

### TC-114: Edited post shows updated content and updated time to everyone
**Category**: Business Rule
**Preconditions**: Post by A; second session as B.
**Steps**:
1. A edits the post text.
2. B reloads the feed.
**Expected Results**: B sees the new text; the share's updated time is newer than its
created time (verifiable via feed API `updatedTime` fields).
**Business Rule**: Share update mutates `shareUpdatedTime`.
**Suggested Layer**: API + E2E

### TC-115: Like/comment counts aggregate across users
**Category**: Business Rule
**Preconditions**: One post; two distinct users (A and B).
**Steps**: A and B each like and comment on the post.
**Expected Results**: Like count = 2, comment count = 2; each user's own like state is
independent (A unliking leaves count 1 and B still liked).
**Business Rule**: Counts are per-share aggregates of distinct user likes/comments.
**Suggested Layer**: E2E (two sessions)

## Security (TC-200–299)

### TC-200: Unauthenticated access to Buzz page redirects to login
**Category**: Security
**Preconditions**: No active session (cleared cookies).
**Steps**: Navigate directly to `/web/index.php/buzz/viewBuzz`.
**Expected Results**: Redirect to `/auth/login` (with `next` param); no feed content
rendered.
**Business Rule**: §1 — deep links force login redirect.
**Suggested Layer**: E2E

### TC-201: Unauthenticated feed API returns 401
**Category**: Security
**Preconditions**: No session cookie / no bearer token.
**Steps**: `GET` the buzz feed endpoint and `POST` a share payload without credentials.
**Expected Results**: Both return 401; no data leak in the body.
**Business Rule**: All Buzz endpoints gate on `buzz_link` permission → 401 for
unauthenticated.
**Suggested Layer**: API

### TC-202: ESS cannot delete another user's post via API
**Category**: Security
**Preconditions**: Post P owned by user A; ESS user B's session; P's share id known.
**Steps**: As B, send the share DELETE request with `data: [<P's shareId>]`.
**Expected Results**: P is NOT deleted — the response's deleted-ids list is empty (the
id is silently filtered out by the allowed-set intersection); P still renders in the
feed.
**Business Rule**: doDelete intersects requested ids with (data-group-allowed ∪ own)
ids; ESS has no delete grant over others.
**Suggested Layer**: API

### TC-203: ESS cannot edit another user's post via API
**Category**: Security
**Preconditions**: Post P owned by A; ESS user B's session.
**Steps**: As B, send the share/post update request targeting P with new text.
**Expected Results**: 403 or failure response; P's text unchanged for all viewers.
**Business Rule**: Update restricted to author.
**Suggested Layer**: API

### TC-204: ESS cannot delete or edit another user's comment
**Category**: Security
**Preconditions**: Comment by A on some post; ESS user B's session.
**Steps**:
1. As B, verify the UI shows no edit/delete affordance on A's comment.
2. As B, send the comment edit and delete API calls with A's commentId.
**Expected Results**: UI affordances absent; API calls rejected (403/failure); comment
unchanged.
**Business Rule**: Comment mutation restricted to its owner (Admin delete excepted).
**Suggested Layer**: API + E2E

### TC-205: Script injection in post text is neutralized (stored XSS)
**Category**: Security
**Preconditions**: Logged in.
**Steps**:
1. Create a text post with body `<script>document.title='xss'</script><img src=x onerror="document.title='xss'">`.
2. Reload the feed in a second user's session.
**Expected Results**: The payload renders as literal text (escaped); no script executes
(document title unchanged, no dialog); page markup shows encoded entities.
**Business Rule**: Post text is data — output must be HTML-escaped by the client.
**Suggested Layer**: E2E

### TC-206: Script injection in comments and reshare text is neutralized
**Category**: Security
**Preconditions**: A post exists.
**Steps**: Add a comment and a reshare whose text contains an XSS payload; view both
as another user.
**Expected Results**: Rendered as inert literal text in both places; no execution.
**Business Rule**: Same output-encoding rule for every user-supplied Buzz string.
**Suggested Layer**: E2E

### TC-207: `javascript:` and data-URI video links are rejected
**Category**: Security
**Preconditions**: API/modal access.
**Steps**: Validate/post `video_link` values `javascript:alert(1)` and
`data:text/html,<script>alert(1)</script>`.
**Expected Results**: `valid: false` / 400; no post created; nothing ever rendered into
an iframe `src`.
**Business Rule**: Allow-list validation only admits http(s) URLs of the listed video
domains.
**Suggested Layer**: API

### TC-208: SQL-style input is stored literally, not executed
**Category**: Security
**Preconditions**: Logged in.
**Steps**: Post text `'; DROP TABLE ohrm_buzz_share;--` and comment `1 OR 1=1`.
**Expected Results**: Both save and render back verbatim; feed continues to work
(subsequent GET 200 with the rows intact).
**Business Rule**: ORM-parameterized persistence; input treated as data.
**Suggested Layer**: API

### TC-209: State-changing Buzz calls require a valid CSRF token / auth context
**Category**: Security
**Preconditions**: A logged-in browser session.
**Steps**: Replay the create-post request with the session cookie but a missing/garbage
CSRF token (for cookie-authenticated web requests).
**Expected Results**: Request rejected; no post created.
**Business Rule**: §1 — `_token` CSRF required on state-changing web requests.
**Suggested Layer**: API

### TC-210: Feed does not leak data beyond Buzz scope for ESS
**Category**: Security
**Preconditions**: ESS session.
**Steps**: `GET` the feed as ESS and inspect the payload.
**Expected Results**: Response contains only Buzz-relevant fields (names, job title,
avatar, post content, counts) — no salaries, contact details, or other PIM fields.
**Business Rule**: Buzz responses are shaped by the share formatter; §2 ESS sees only
permitted data.
**Suggested Layer**: API

## Negative (TC-300–399)

### TC-300: Whitespace-only text post is rejected
**Category**: Negative
**Preconditions**: Composer open / API access.
**Steps**: Attempt a status post whose text is `"   "` (spaces/newlines only).
**Expected Results**: Post button remains disabled or submission fails validation; no
post appears in the feed.
**Business Rule**: `notEmpty` on status text (trim behavior — if the API accepts it,
flag as a bug candidate).
**Suggested Layer**: API + Component

### TC-301: Invalid post type via API is rejected
**Category**: Negative
**Preconditions**: API access.
**Steps**: POST a share with `type: "poll"` (not in the allowed set).
**Expected Results**: 400 Bad Request; nothing created.
**Business Rule**: `type` ∈ {status, photo, video, reshare(, kudos)}.
**Suggested Layer**: API

### TC-302: Corrupt base64 photo payload is rejected
**Category**: Negative
**Preconditions**: API access.
**Steps**: POST `type=photo` with a photo whose `base64` is random text (not decodable
to an image) but valid `name`/`type`/`size`.
**Expected Results**: 400 — the `imagecreatefromstring` check fails; no post created.
**Business Rule**: base64 content must decode to a real image.
**Suggested Layer**: API

### TC-303: Renamed non-image (txt renamed to .jpg with image/jpeg type) is rejected
**Category**: Negative
**Preconditions**: API access; text file bytes base64-encoded, declared `image/jpeg`.
**Steps**: POST the photo payload.
**Expected Results**: 400 — content sniffing (image decode) rejects it despite the
spoofed extension/MIME.
**Business Rule**: Validation checks actual decoded content, not just declared type.
**Suggested Layer**: API

### TC-304: Malformed video URL string is rejected
**Category**: Negative
**Preconditions**: Share Video modal / API.
**Steps**: Enter `not a url`, `htp:/broken`, and an empty string as `video_link`.
**Expected Results**: Each fails validation (`valid: false` / 400); Share stays
disabled; no post created.
**Business Rule**: `isUrlValid` requires a parseable URL on an allowed domain.
**Suggested Layer**: API

### TC-305: Commenting on a deleted post fails
**Category**: Negative
**Preconditions**: Post P created then deleted; its shareId captured.
**Steps**: POST a comment against P's shareId.
**Expected Results**: Error response (400/404); no orphan comment created.
**Business Rule**: Comments require an existing share.
**Suggested Layer**: API

### TC-306: Liking a deleted post fails
**Category**: Negative
**Preconditions**: Deleted post's shareId captured.
**Steps**: POST a like against it.
**Expected Results**: Error response; no like recorded.
**Business Rule**: Likes require an existing share.
**Suggested Layer**: API

### TC-307: Deleting a nonexistent share id is a safe no-op
**Category**: Negative
**Preconditions**: Admin API session; an id far beyond the current max (e.g. 99999999).
**Steps**: Send share DELETE with `data: [99999999]`.
**Expected Results**: No 5xx; response succeeds with an empty deleted-ids list (or
clean error); feed unaffected.
**Business Rule**: Requested ids are intersected with existing/allowed ids.
**Suggested Layer**: API

### TC-308: Editing own post to empty text is rejected
**Category**: Negative
**Preconditions**: Own text post exists.
**Steps**: Edit the post, clear all text, attempt to save.
**Expected Results**: Save blocked (button disabled or `Required` validation); the
original text remains after cancel/reload.
**Business Rule**: Status text non-empty applies on update as well.
**Suggested Layer**: E2E

### TC-309: Invalid feed query parameters return 400, not 5xx
**Category**: Negative
**Preconditions**: Authenticated API session.
**Steps**: GET the feed with `pageNo=0`, `pageNo=-1`, `limit=-5`, `limit=abc`,
and `pageNo` without `limit`.
**Expected Results**: Each invalid combination returns 400 Bad Request (limit is
mandatory with pageNo; values must be positive ints); no server error.
**Business Rule**: GET validation — `limit` positive, required when `pageNo` present.
**Suggested Layer**: API

### TC-310: Reshare with empty string reshare_text is rejected; omitted is accepted
**Category**: Negative
**Preconditions**: A post to reshare; API access.
**Steps**:
1. POST reshare with `reshare_text: ""`.
2. POST reshare with the field omitted entirely.
**Expected Results**: (1) 400 — the optional field, when present, must be non-empty.
(2) 201 — reshare without text succeeds.
**Business Rule**: `reshare_text` optional but `notEmpty` when supplied.
**Suggested Layer**: API

## Edge Cases (TC-400–499)

### TC-401: Post text at the 65535-character boundary
**Category**: Edge Case
**Preconditions**: API access (UI textarea may be impractical at this size).
**Steps**:
1. POST a status with exactly 65535 characters.
2. POST a status with 65536 characters.
**Expected Results**: (1) 201 created; text stored intact (verify via GET).

**Business Rule**: `length(0, 65535)` on status text.

**Suggested Layer**: API

### TC-406: Double-click on Post creates exactly one post

## Out of Scope / Notes

- **Kudos posts** (`type=kudos`, kudos types 1–10, receiver-must-exist 404 rule) exist
  in the discovered code but belong to the **Enterprise** feature set
  (`buzz_kudos` config flag). They are excluded from this open-source suite; if the
  target instance enables kudos, extend with: happy-path kudos post, receiver-not-found
  404, invalid kudos_type 400, and kudos rendering (background image + receiver card).
- **Email notifications** (recent-posts digest) are backend/cron behavior — not covered
  here; cover in an integration suite if SMTP is wired on the test instance.
- Exact UI copy (button labels, empty-state text, error wording) must be confirmed on
  the live instance when implementing; scenarios assert behavior, with copy assertions
  to be pinned during implementation (as done for the Dashboard suite).
