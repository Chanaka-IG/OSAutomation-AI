# Test Strategy: E2E Leave Lifecycle — Add Entitlement → Assign to ESS → Apply as ESS → Action as Admin/Supervisor

> Input: `docs/test-scenarios_E2E test for Leave. Add Leave entitlement -> Assign entitlement for ESS -> Apply leave as ESS -> Leave actions as Admin or supervisor.md` (40 scenarios)
> Sources: `orangehrm-opensource-domain` (business-rules.md §4/§5, api-reference.md), `playwright-best-practices`, existing suites `tests/leave/*.spec.ts`.
> Generated by `test-strategy` skill.

## Context

This feature is explicitly a **cross-role, multi-page journey** — the rare case where E2E is the *primary* layer, not the last resort. The chain (Admin entitles → ESS applies → Admin/Supervisor actions) crosses three sessions and four pages; its value is in the integration, so the golden paths MUST be E2E.

However, the **escrow math, status-transition rules, and permission enforcement** all live in the PHP backend (`orangehrmLeavePlugin/Api`: `LeaveEntitlementAPI`, `LeaveRequestAPI`, `EmployeeLeaveRequestAPI`) and are fully exercisable via `src/api/orangehrmOSAPI/LeaveEntitlementsApi.ts` / `LeaveRequestsApi.ts` / `AuthApi.ts` (per-user session login already exists). Those are pushed DOWN to API.

No Unit/Component candidates: we test a deployed PHP+Vue app black-box; there is no in-repo pure logic to unit test, and OXD components are upstream-tested. (Frontend-only display states ride along inside E2E journeys rather than standalone Component tests.)

## Contested Assignments — Rationale

- **TC-300/302/303 (form validation) kept at E2E despite the "validation → API" rule**: the assertion target is the *OXD inline rendering* (`Required` under the field), which the API layer cannot see. The API-side input validation is separately covered by TC-301/over-balance mirrors. Both layers, different oracles.
- **TC-104/109 at E2E with API oracle**: the balance widget is known-flaky (memory: don't assert its text). The deterministic oracle is the entitlement-balance API delta, but the *attempt* must go through the UI because the requirement is about what an ESS user can do on the Apply page.
- **TC-008 (bulk assign) at E2E not API**: the Multiple-Employees toggle, filter, and affected-count confirmation modal are the risk surface; the underlying POST is trivial.
- **TC-402 at API**: number-size boundary has zero UI-specific behavior — pushed down.
- **TC-105 weekend math at API**: previously validated via UI in `assign-leave.spec.ts`; duplicating at E2E adds minutes for no new information.

## Anti-Patterns Found in Existing Tests

- `tests/leave/leave.spec.ts` (legacy) asserts success via page-heading visibility in places — heading stays visible on success AND failure; toast (`.oxd-toast--success`) is the reliable oracle. New tests must not copy this.
- Existing suites individually re-seed similar fixtures (employee + entitlement) per file; for this chained suite use **one serial describe with shared seed** (employee, supervisor, entitlement) to avoid N× seeding cost.
- Avoid 2026-08-06 (seeded global holiday) for any single-day request except TC-305 where it is the fixture.
