> Input: `docs/test-scenarios_buzz.md` (79 scenarios: 18 happy path, 16 business rule,
> 11 security, 11 negative, 11 edge, 12 UI state)
> Sources: `orangehrm-opensource-domain` (business-rules.md §§1–2, 9–10;
> api-reference.md auth/error contract), discovered backend code
> (`symfony/plugins/orangehrmBuzzPlugin` — `BuzzPostsEndpoint`, `CommentEndpoint`,
> `CommentsEndpoint`, `LikesEndpoint`, `VideoLinkValidatorEndpoint`,
> `BuzzConfigService`, `BuzzService`), `playwright-best-practices`, existing suites
> (`tests/api/pim-employees.spec.ts` session-API pattern, `tests/dashboard/dashboard.spec.ts`).
> Generated by `test-strategy` skill.

## Context

Buzz is a **validation-heavy social feed**: almost every business rule lives in the
backend endpoint validators (`getValidationRuleForPost/Delete` in `BuzzPostsEndpoint`,
`commentText` rules in `Comment(s)Endpoint`, duplicate-like guards in `LikesEndpoint`,
the video-domain allow-list in `ShareEndpointHelper::isUrlValid`). Those rules are
deterministic request/response contracts — they belong at the **API layer**. The UI's
unique risk surface is rendering and interaction state (composer/modal enablement,
like toggles, ⋮ menu scoping, reshare card composition, XSS output-encoding), which
stays at **E2E**.

**No Unit/Component layers**: the app under test is a deployed black-box instance (no
access to run its Vue components or PHP classes in isolation; OXD is upstream-tested) —
same rationale as the Dashboard and Leave strategies. Scenarios the scenario doc tagged
"Component" (button/modal enablement: TC-100, TC-101, TC-108, TC-502) are re-mapped:
the *rule* goes to API, the *widget state* folds into an E2E journey.

**Endpoint note for implementers**: the scenario rules are traced from the backend
plugin code (paths shown as `/api/buzz/shares`, `/api/buzz/validateVideoLink`). The
live instance exposes the v2-style routes (the Dashboard suite already consumes
`GET /api/v2/buzz/feed`). Resolve the exact create/like/comment/delete paths from the
browser network log on first implementation and pin them in `test-data` (the same
runtime-resolution convention used by `leave-e2e-lifecycle.spec.ts`).

Shape check: the base (API) is wider than the top (E2E), and E2E folding compresses 38
scenario assertions into ~19 journeys — pyramid, not ice-cream cone.

## Layer Assignments

### E2E (38 scenarios → ~19 test functions)

Folded into journeys per `playwright-best-practices` (one user goal per test; assert on
toasts/locators, wait out `.oxd-loading-spinner`). Seed prerequisite posts/likes via the
API client, not the UI.

**J1 — Post lifecycle (own text post)**: create → verify at feed top → edit → verify
update → attempt edit-to-empty (blocked) → delete-cancel → delete-confirm.
Covers **TC-003, TC-014, TC-308, TC-015, TC-508, TC-509** (+ unicode text used as the
post body covers **TC-404**).

**J2 — Engagement on a seeded post**: like → icon state → unlike → comment → collapse/
expand → like comment → edit comment → delete comment.
Covers **TC-007, TC-008, TC-505, TC-009, TC-506, TC-010, TC-011, TC-012**.

**J3 — Reshare journey** (user B reshares A's seeded post): modal → post → card shows
both identities → original share-count increments.
Covers **TC-013, TC-511**.

**J4 — Feed tabs & scroll** (seeded: 1 fresh, 1 most-liked, 1 most-commented post,
plus >10 filler posts via API): tab ordering, active-tab persistence through a like,
infinite scroll appends without duplicates.
Covers **TC-016, TC-510, TC-017**.

**J5 — Media posts**: photo post with 1 image; photo modal remove-before-post; photo
post with exactly 5 images (gallery render); video modal state machine
(empty→invalid→valid+preview) and YouTube post with embed.
Covers **TC-004, TC-504, TC-402, TC-005, TC-503** (~3 tests).

**J6 — Roles & affordances**: ESS session sees Buzz and can post (TC-002); ⋮ menu shows
Edit/Delete only on own posts, nothing/limited on others' (TC-109, TC-507); Admin
deletes an ESS post from the UI (TC-110). (~2 tests.)

**J7 — Landing & load states**: Admin menu → Buzz renders composer + feed, skeleton
loader resolves (TC-001, TC-501). Empty-feed state (TC-500) is **conditional** — only
runnable on an instance that can be drained of posts; implement as a tab/filtered empty
state with a `test.skip` guard otherwise.

**J8 — Security rendering**: unauthenticated `/buzz/viewBuzz` → login redirect
(TC-200); stored-XSS payloads in a post, a comment, and a reshare render inert as
literal text in a second user's session (TC-205, TC-206 — one test, three surfaces).

**J9 — Composer state & robustness**: Post button disabled↔enabled tracking input
(TC-502, subsumes the UI half of TC-100); double-click creates exactly one post
(TC-406); long-unbroken-string and multi-line rendering without layout break (TC-405).

## Contested Assignments — Rationale

- **TC-402 (exactly 5 photos) stays E2E, TC-102 (6 photos) goes API**: the accept-side
  boundary is worth paying for once in the UI because the 5-image *gallery render* is a
  distinct frontend risk; the reject side is a pure validator response — API.
- **TC-111/TC-112 (delete cascades) pushed to API**: the cascade is entirely
  `doDelete`/DAO behavior; UI deletion mechanics are already covered by J1/J6. Verifying
  reshare disappearance via feed GET is deterministic and fast.
- **TC-115 (cross-user count aggregation) at API, not two browser sessions**: two
  request contexts prove the aggregation rule; count *rendering* is already asserted in
  J2. A dual-browser E2E would triple runtime for no new risk coverage.
- **TC-205/TC-206 (XSS) stay E2E deliberately** (exception to "push validation down"):
  the backend intentionally stores arbitrary text (TC-208 proves that at API); the
  vulnerability, if any, is in frontend *output encoding*, which only a real DOM proves.
- **TC-410 (timezone display) is API-first with the display assertion deferred**:
  relative-time labels ("a few seconds ago") and viewer-timezone rendering are flaky to
  assert cross-locale; the API timestamp consistency check catches the data-level bug,
  and the display check is left as an exploratory/manual note.
- **TC-100/TC-108/TC-502 split**: the *rule* (notEmpty) is API; the *disabled-button UX*
  is one cheap E2E assertion in J9 — this avoids the classic "input validation at E2E"
  anti-pattern while still covering the visible behavior.
- **TC-006 (multi-provider video) at API**: `validateVideoLink` returns the embed URL —
  asserting the rewrite for youtu.be/Vimeo needs no browser; one provider's full embed
  render is already covered by TC-005 in J5.
- **TC-209 (CSRF) at API**: replaying a cookie-authenticated create with a broken
  `_token`/CSRF header is a request-layer concern (api-reference: 401 "Invalid CSRF
  token"); no UI journey exists for it.

## Anti-Patterns Found in Existing Tests

- **No Buzz coverage exists at all** — the only references are the Dashboard widget
  (`tests/dashboard/dashboard.spec.ts` asserts "Buzz Latest Posts" renders) and
  `DashboardPage.ts`. A critical gap: the Dashboard widget consumes
  `GET /api/v2/buzz/feed`, so Buzz regressions currently surface only as incidental
  dashboard flake.
- The API layer folder (`tests/api/`) contains a single suite (PIM employees). The 41
  Buzz API scenarios should follow its established pattern (unauthenticated context for
  401s, `orangehrmAdminApi`/ESS fixture for session calls, `test-data` path constants) —
  do **not** invent a second API-auth mechanism.
- Existing UI suites correctly avoid re-testing login; the Buzz suites must likewise
  start from the authenticated fixture and never assert login mechanics.
- Watch the repo-wide serial-worker constraint (`workers: 1`, shared instance): Buzz
  tests mutate a **global shared feed** — every test must create its own uniquely-named
  posts and clean up via API `afterEach` (or scope assertions to unique text), because
  the nightly demo reset is the only other cleanup.

## Handoff Notes for `/generate-tests`

1. Build a `BuzzApi` client in `src/api/` (create post [status/photo/video/reshare],
   like/unlike share & comment, comment CRUD, delete shares, feed GET, validate video
   link) — resolve v2 paths from the live network log first.
2. Suite layout: `tests/api/buzz.spec.ts` (41 scenarios) and `tests/buzz/*.spec.ts`
   split by journey (J1–J9).
3. Config-dependent boundaries (TC-103/403 size cap, TC-402/102 photo count if the
   instance differs) must read the effective limit at runtime or from `test-data`, not
   hard-code megabytes.
4. Kudos scenarios remain out of scope unless the instance enables `buzz_kudos`
   (enterprise flag) — guard any future kudos specs with a capability probe.
